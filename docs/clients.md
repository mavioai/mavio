# Mavio Clients

> English | [简体中文](clients.zh-CN.md)

> Related: [Architecture](architecture.md) · [Domain Model](domain.md) · [Roadmap](roadmap.md) · [Development](development.md) · [AGENTS.md](../AGENTS.md)

> Mavio's clients are a web UI embedded in the server binary and a native app for each way people watch: iPhone and iPad, Apple TV, Mac, Android phones and tablets, Android TV, and desktops on macOS, Windows and Linux. The server makes the decisions; the clients declare what they can play, play it, and keep what they need offline. A shared Rust core gives every native app one implementation of the connection, event, offline and playback-reporting logic. The clients are built in phase P21 of the [Roadmap](roadmap.md).

---

## 1. Overview

Each app is built for one interaction model — touch, the television remote, the pointer and keyboard of a desktop — rather than stretched across several. What does not depend on the interaction model is shared below the apps.

| App | Technology | Devices |
| :--- | :--- | :--- |
| `apps/web` | React + Vite + TanStack Router / Query + Base UI + Tailwind CSS, embedded in the server with `//go:embed` | Browsers |
| `apps/ios` | Swift, SwiftUI (UIKit where SwiftUI falls short) | iPhone and iPad, one universal app |
| `apps/tvos` | Swift, SwiftUI and UIKit | Apple TV |
| `apps/macos` | Swift, AppKit (SwiftUI where it fits) | Mac |
| `apps/android` | Kotlin, Jetpack Compose | Android phones, tablets and foldables |
| `apps/android-tv` | Kotlin, Compose for TV | Android TV and Google TV |
| `apps/desktop` | Go, [MyGo](https://github.com/egoist/mygo) native UI, libmpv | macOS, Windows and Linux |

| Library | Contents | Used by |
| :--- | :--- | :--- |
| `libs/client-ts` | TypeScript: Connect client (`connect-es`) and TanStack Query hooks | `apps/web` |
| `libs/client-rust` | Rust: servers, sign-in, events, offline store, playback reporting, downloads | Every native app: through UniFFI from Swift and Kotlin, through a C ABI from Go |
| `libs/apple` | Swift packages: the core's Swift API and app services, the player, shared SwiftUI components | `apps/ios`, `apps/tvos`, `apps/macos` |
| `libs/android` | Kotlin modules: the core's Kotlin API and app services, the player, shared Compose components and the server settings' screens | `apps/android`, `apps/android-tv` |
| `libs/design` | Design tokens (DTCG JSON), icons, the logo, component specifications and strings, compiled for every client | Every client |

## 3. Server and Clients

The server owns every decision that depends on the library, the user or other devices; the clients own what depends on the device.

| Concern | Where | How |
| :--- | :--- | :--- |
| Playback decision | Server | `PlaybackService` decides direct play, remux or transcode from the client's `ClientCapabilities` with `libs/media/decision`, together with the user's stream preferences, bitrate cap, transcoding permission and playback limits ([Architecture §11](architecture.md#11-api-and-authentication-appsserver)) |
| Capabilities | Client | Probed with the platform's own APIs: AVFoundation and VideoToolbox, `MediaCodecList` and `Display.HdrCapabilities`, the browser's `MediaSource.isTypeSupported` and `canPlayType`, and the decoders of the bundled second engines (AetherEngine, libmpv). A client playing with two engines declares what either plays, so that the server processes media only when neither can (§4.2) |
| Progress | Client reports, server records | Reported through `PlaybackService` every 10 seconds while playing and on pause, seek and stop; the server ends a playback five minutes after its last report |
| Live updates | Server pushes | One `EventService` stream per device: item and library changes, user data, sessions, remote-control commands and SyncPlay. Clients reconnect with backoff and do not poll |
| Media and images | Plain HTTP | The URLs the server signs for the session ([Accounts §5.4](accounts.md#54-media-urls)), so players need no headers |
| Sign-in | Server | Sessions bound to the device key, with short-lived bearer tokens; televisions sign in Mavio accounts with a code at mavio.dev/link, and standalone servers' users with Quick Connect |
| Home | Server builds, client merges | Each server builds its hubs for the user with `HubService` ([Architecture §11](architecture.md#11-api-and-authentication-appsserver)); the client merges the hubs of every server it is signed in to (§5.4) |
| Finding servers | Client | UDP discovery on port 7359 on the local network, or an address typed in |
| Acquisition, discovery and requests | Server | The server's own services; clients call nothing else |

## 4. Platforms

### 4.1 Web (`apps/web`)
* **Role**: every feature — browsing, playback, requests, administration and the first-run setup — with no installation.
* **Serving**: Vite builds into `apps/server/internal/webui/dist`, which the server embeds with `//go:embed` and serves at `/`, with the SPA's routes falling back to `index.html`. The directory holds only a `.gitkeep` in the repository; a server built without the web UI serves a page saying so. Nx makes the server's `build` depend on the web's. The API reference stays at `/api`. Built with `VITE_MAVIO_DEV_URL`, the base URL of mavio.dev's API, the same web UI is app.mavio.dev, which no server serves and which signs in Mavio accounts alone.
* **Servers**: a standalone server's web UI reaches that server alone. A Mavio account's web UI, a server's or app.mavio.dev, reaches every server of the account (§5.4): it signs in to each at the first of the URLs the server published that answers, over HTTPS only from a page served over HTTPS — the server serving the page at the page's own address — and calls them cross-origin; servers allow any origin on every route, which take bearer tokens and signed media URLs and never cookies. The device key is a non-extractable WebCrypto Ed25519 key in IndexedDB, and the sessions and the user's order of servers are kept in the browser's local storage; the transport refreshes an access token before it expires, or once the server rejects it, and signs a Mavio account in again where a server no longer refreshes its session.
* **Signing in** ([Accounts §6](accounts.md#6-signing-in)): a new server opens `/setup`, which chooses its mode ([Accounts §2](accounts.md#2-server-modes)) and then signs a Mavio account in, which claims the server, or creates its administrator (`?step=admin`); on a television it shows the server's address to open on a computer or phone. `/sign-in` signs in the way the server does. In mavio.dev mode it signs in the server's administrator through mavio.dev's authorization page and points everyone else to app.mavio.dev; mavio.dev comes back to `/auth/callback`, which returns to where the sign-in started. A standalone server signs in with a password, then the code of the user's authenticator app (`?step=totp`), a passkey of the serving server's host, or Quick Connect (`?step=quick`); the user menu switches between its users with their PINs, and settings manage the user's password, changed with the current one, which signs the user out elsewhere, passkeys, authenticator app and PIN. A television signs a Mavio account in with a code to enter at mavio.dev/link. Each step has its own address, so that the browser's Back, Escape and a remote's Back return to the step before. The steps lie on a wall of posters drawn from gradients, tilted and blurred under a veil that is dark or light with the theme: in a card on a wide window and a television, across the whole screen on a phone. Signing out ends every session of the sign-in.
* **Screens**: the layout follows the window's width (§6.3), and television mode is a setting of the browser. Settings are in sections — Appearance, Playback, Subtitles & Audio, Assistant, Servers, Account, Devices and Issues — beside their own sidebar, or listed first on a phone and a television ([Television §6.6](tv.md#66-settings)); those of the browser (appearance, the UI's language, television mode, the sidebar and its width, the highest quality and playing the next episode) are kept in its local storage, and the audio and subtitle languages in the user's preferences on each server. The sidebar and the settings' sidebar share one width, the layout's by default, dragged by their edge between 200 and 400 px and restored by double-clicking it. The UI's language, under Appearance, follows the browser's languages by default, and the page reloads in the language chosen; discovered titles are named in it too. In television mode the arrow keys move focus to the nearest element in their direction, and Escape and Backspace go back.
* **Navigation**: the browser's history holds the pages the user opened, and nothing else. A page asked for before signing in is replaced by signing in, which opens it once signed in (`/sign-in?redirect=`, a path of the web UI alone). What follows from an action takes the place of the page rather than adding to the history: the page of what was just created, the list after deleting, another server's settings, an address corrected, a library's filters and order, and an item another device asked to play while one plays. What a page shows is kept in its address, which Back and a reload return to: a series' season and the version chosen, the kind of a person's titles, and the tabs and filters of the settings' pages; choosing one replaces the page in the history. An overview, biography or list of studios expanded stays so as Back returns to the page, where a page opened anew starts with them folded. A link up to the page above, as a settings page's to its list, shows that page where it was scrolled when it was left. A page stays as the window crosses between the phone's layout and the wider one, keeping what it holds. Each page the sidebar opens, and on a phone each tab and Search, where a library is a page of Libraries, is a place that keeps the pages opened from it, as the Apple TV app's: choosing another place and coming back returns to the page last shown there, scrolled where it was left, and the sidebar or the tab bar marks the place of the page shown; choosing the place shown returns to its top. In the wider layouts a page opened from another has a round button of glass 12 px from the content's top and left edges at every width, over its hero where it has one, and on a phone Back in place of the header's wordmark; either goes back to the page it was opened from within its place, or up a level when it was opened directly; the places have none, and the sidebar or the tab bar alone moves between them. The settings and the player load as they are first opened, or as a link to them is pointed at. Every page names itself in the browser's tab and history by its heading; but on the television, a page opened moves focus to its heading, or has assistive technology announce its title where it has none. An address that names nothing, or an item, person or title no longer there, shows Not Found, with a way home. Back with a dialog open closes the dialog and stays on the page under it. Leaving a form or an editing dialog whose changes are not saved asks first, whether by a link, Back, Escape or closing the tab.
* **Controls**: every control is drawn by the web UI itself, the same in every browser and operating system: [Base UI](https://base-ui.com) gives selects, menus, dialogs, alerts, tooltips, switches, checkboxes, sliders, number fields, fields with suggestions, radio groups, tabs, toggles, progress bars and disclosures their behavior and accessibility (focus kept in and returned, the arrow keys, typing to an item, Escape, a press outside), and Tailwind CSS draws them with the design tokens; `src/controls` wraps them for the screens, which use no control of the browser's own look. Popups are portaled above the page, and on a television menus are frosted glass with larger items that open on the item chosen, and Back closes a popup as Escape does.
* **API**: `libs/client-ts`, on `connect-es` v2 and `protobuf-es` v2 with the code generated from `libs/proto`, and TanStack Query for caching and invalidation, driven by the event stream: a library change refreshes the queries of the libraries' items and of what they make, such as whether a discovered title is in a library, and a new stream all of the server's; a change of user data is put into the cached items and refreshes only the lists it chooses or orders, and marking an item played or favorite shows at once, undone should the server refuse it. The tabs of a browser share its session, whose stream the tab in front holds, unless the tab holding it plays, passing its events on to the other tabs, which only refresh their queries with them. The queries of the libraries stay fresh for five minutes, since the events refresh them, a grid keeps its items while another order or filter loads, and resting the pointer on an item's card fetches the item ahead of its page.
* **Playback**: hls.js on browsers with Media Source Extensions, the native HLS player on Safari; capabilities from `MediaSource.isTypeSupported` and `canPlayType`. ASS subtitles keep their styling with JASSUB (libass in WebAssembly). For what a browser cannot play without a transcode, the player offers to open the playback URL in an external player (mpv, VLC, IINA).
* **Assistant**: the first client of [Assistant](assistant.md) (§9.2 there): the grammar of `libs/intent` as WASM through `libs/client-ts`, the microphone on secure pages only, captured with the browser's echo cancellation into voice sessions through the server, and the answers' speech they stream.

### 4.2 Apple (`apps/ios`, `apps/tvos`, `apps/macos`, `libs/apple`)
* **One app per interaction model.** iPhone and iPad are one universal app, as the App Store expects, with layouts of their own on iPad: the tab bar at the top, multiple columns, several windows, Stage Manager, the pointer and hardware keyboards. Apple TV is its own app, built around the focus engine and the remote at ten feet, with the Top Shelf. The Mac is its own app in AppKit, the toolkit that gives a player full control of windows, the menu bar, full screen, the trackpad and several players at once.
* **`libs/apple`**, Swift packages shared by the three apps:
  * `MavioKit`: the core's Swift API with the app services above it — accounts, capability probing, downloads with a background `URLSession`, Now Playing (`MPNowPlayingInfoCenter`, `MPRemoteCommandCenter`) — and the messages of the server's API, `MavioProto`, generated with [swift-protobuf](https://github.com/apple/swift-protobuf) (Apache-2.0): the screens the core does not model, the settings, call the server's API with them through the core (`callServer`), as the desktop app does (§4.4);
  * `MavioPlayer`: one player interface with two engines, and Picture in Picture;
  * `MavioUI`: SwiftUI components each app composes in its own way (artwork, posters, rows), and the design tokens; artwork is loaded and cached by [Nuke](https://github.com/kean/Nuke)'s `LazyImage` (MIT);
  * `MavioScreens`: the screens the iPhone and iPad app and the Mac app share — Home, the libraries, search, the details, Discover, a person, the downloads, signing in and the user's settings — with their routes, each app composing them in a shell of its own;
  * `MavioAdmin`: the settings' Server group, the server's sections and their administration, shared by the three apps, leaving out on each what its platform lacks (saving files on Apple TV).
* **Player engines**, in order of preference: AVPlayer, then AetherEngine, then the server's processing.
  * **Capabilities**: the app declares in `direct_play` the profiles AVPlayer plays and those AetherEngine plays. The server therefore plays a source directly whenever either engine can, and remuxes or transcodes it only when neither can.
  * **Choice**: a source played directly goes to AVPlayer when AVPlayer plays it as it is, else to AetherEngine; what the server remuxes or transcodes is HLS, which goes to AVPlayer, unless the subtitles chosen come as a file of their own, which AetherEngine draws over the HLS it plays.
  * **AirPlay**: while AirPlay is in use, the app declares AVPlayer's profiles alone.
  * **AVPlayer**, the first engine, plays what AVFoundation plays — MP4 and MOV with H.264, HEVC, AV1 where the hardware decodes it, Dolby Vision and HDR10, AAC, AC-3 and E-AC-3 with Atmos — and every HLS stream the server makes. It brings system Picture in Picture, AirPlay, `AVPlayerViewController` on iOS and tvOS, and frame rate and dynamic range matching on tvOS (`AVDisplayCriteria`).
  * **[AetherEngine](https://github.com/superuser404notfound/AetherEngine)**, the second, a Swift package from the branch `v7.39.0-mavio` of its fork `mavioai/AetherEngine`, direct plays what AVFoundation does not, such as Matroska with styled ASS and PGS subtitles, VP9, DTS and TrueHD, sparing the server a transcode. FFmpeg demuxes and VideoToolbox decodes (dav1d and libavcodec where the hardware cannot), and frames reach Apple's own display stack — an `AVPlayerLayer` on its native path, an `AVSampleBufferDisplayLayer` on its software path — with no renderer of its own: HDR10, HDR10+, HLG and Dolby Vision (profiles 5, 7 as 8.1, and 8) go to the display as they are, through EDR on the Mac and iPad and with display criteria on tvOS. DTS and TrueHD are converted to E-AC-3 5.1 and E-AC-3 with Atmos is passed through. Subtitles arrive as cues that `MavioPlayer` draws over the picture: styled text runs and bitmaps, and for ASS the raw event lines, the script header and the embedded fonts, which [libass](https://github.com/libass/libass), built for the three platforms, renders with their authored styling: `ASSRenderer` takes the fonts the server lists as the item's attachments and finds the rest with Core Text, and draws each frame's subtitles into an image over the picture. Its FFmpeg is embedded as dynamic LGPL frameworks, the only FFmpeg in the app. The fork differs in one respect: it calls libdovi, which parses and converts Dolby Vision metadata, through the core, whose library exports libdovi's C API (the crate `dolby_vision`, by the feature `dovi` of `mavio-uniffi`), instead of linking LibDovi, a static Rust library, so the app links one Rust standard library. The engine's optional traits, TrueHD and DTS:X object audio, the Profile 7 dual-layer composer and Dolby Vision stills, are off.
* **Sign-in**: a server's address, or a server found nearby, signs in a standalone server's user with a password, as its first user or with Quick Connect; a server in mavio.dev mode signs a Mavio account in at its mavio.dev in an `ASWebAuthenticationSession`, which comes back to a loopback address of the core (with PKCE), or with a link code approved at mavio.dev/link. The profile shows the Mavio account and signs it out, which forgets its servers.
* **Launch**: the launch screen is the mark on the system's background, and the app keeps it until Home can be drawn whole — its rows from the offline store and the first screen's images — for at most two seconds, then the mark grows as it fades into Home, so that no placeholder flashes by. Nuke keeps the images on disk, keyed by their URLs without the servers' signatures; artwork still loading is a plain fill into which it fades, and only artwork there is none of shows the icon of what it is.
* **Accounts and downloads**: the device key and each server's session are kept in the Keychain, and the core's database holds the rest. A download is the source file fetched with a background `URLSession`, so it continues while the app is suspended; a downloaded item plays from the device with no server, and the progress made offline is replayed to its server when the server answers again (§5.1).
* **Subtitles**: an HLS stream carries text subtitles as WebVTT renditions, which AVPlayer shows itself. With AetherEngine, `MavioPlayer` lays the cues out inside the picture rather than the screen, so they stay over the video at any aspect ratio and orientation.
* **Picture in Picture**: `AVPictureInPictureController` only, which is public and allowed in the App Store. AVPlayer gives it directly, and AetherEngine through its `AVPlayerLayer` or its `AVSampleBufferDisplayLayer` content source. tvOS shows no Picture in Picture of a sample buffer display layer, so entering it while AetherEngine plays on its software path starts the playback again on AVPlayer, the server processing the source.
* **What the iPhone and iPad app leaves out**, which the App Store does not accept or might not: acquisition — the indexers and download clients, the quality profiles, custom formats and rules, Wanted, the download clients' queue, an item's acquisition and the indexer search (§6.3.11, §6.3.16–§6.3.18, §6.3.31) — the subtitles' settings, with searching the subtitle providers for an item (§6.3.12, §6.3.21), proxies and challenge solvers (§6.3.30), Discover's requests, plugins (§6.3.3), AI, with its providers and the assistant's settings, and the users' AI conversations (§6.3.13, §6.3.26); with them, Overview's plugin containers and, in Tasks, the tasks and jobs of acquisition, requests, subtitles and plugins. It opens none of them in a browser either; the rest of the settings it has as the web UI does.
* **The Mac app keeps all of it**, being distributed outside the App Store: its settings are the web UI's desktop layout, beside a sidebar of their own that returns Home and lists, flat with a colored tile each, the account, the Advanced group (indexer search and the AI conversations, for the server's administrators), This Device, and the sections of the server chosen, its menus' sections in their place; the section chosen is a page of the web UI's groups, at most 900 points wide, and Discover has its requests as the web UI's. The streams the core does not model, such as an AI conversation's answer, reach the screens through the core's server-streaming call.

### 4.3 Android (`apps/android`, `apps/android-tv`, `libs/android`)
* **One app per interaction model.** Phones, tablets and foldables share an app in Compose with adaptive layouts; Android TV and Google TV have their own in Compose for TV, built around D-pad focus, with Watch Next and channels on the home screen. They are published as one Play listing under one application ID, `dev.mavio.app`, the TV app for the TV form factor; both run on Android 8.0 (API 26) and later.
* **`libs/android`**, Gradle modules shared by both apps, which include it as a composite build:
  * `core`: the core's Kotlin API with the app services above it — accounts, capability probing, downloads with WorkManager — and the messages of the server's API, generated in Kotlin lite at build time by protoc from Maven at the version of the protobuf runtime (BSD-3-Clause): the screens the core does not model, the settings, call the server's API with them through the core (`callServer`), as the Apple apps do (§4.2). It declares the `INTERNET` permission and `ACCESS_LOCAL_NETWORK`, which Android 17 requires to reach an address on the local network, where most servers are; the apps request the latter before discovery or sign-in, and allow cleartext HTTP (`usesCleartextTraffic`), which Media3 otherwise refuses, as servers on the local network serve their media over plain HTTP;
  * `player`: one player interface with two engines, behind a `MediaSessionService` for background playback and system controls, and Picture in Picture, which on Android takes any `SurfaceView`; and the player following a SyncPlay group (§6.3.24);
  * `ui`: shared Compose components and the design tokens;
  * `admin`: the screens of the settings' Server group for a server's administrators and those editing an item's metadata, identifying it and choosing its images, on `ui`, which both apps open, each in its own layout.
* **Launch**: as on the iPhone (§4.2), the SplashScreen API keeps the mark on the background until Home can be drawn whole — its rows and the first screen's images — for at most two seconds, then the mark grows as it fades into Home. Coil keeps the images on disk, keyed by their URLs without the servers' signatures; artwork still loading is a plain fill into which it fades.
* **Player engines**, in order of preference as on Apple platforms: Media3, then libmpv, then the server's processing.
  * **Capabilities**: the app declares in `direct_play` the profiles Media3 plays on the device and those libmpv plays, so that the server remuxes or transcodes a source only when neither can.
  * **Choice**: a source played directly goes to Media3 when Media3 plays it as it is, else to libmpv; what the server remuxes or transcodes goes to Media3.
  * **Dolby Vision and HDR**: the libmpv profiles exclude Dolby Vision video and, on devices with HDR output, HDR video, which Media3 plays to the display and libmpv only tone maps.
  * **Media3** ExoPlayer, the first engine, plays Matroska and MP4 in the formats the device decodes, the audio formats the platform lacks (DTS, TrueHD and the like) through its FFmpeg decoder extension, built from source with FFmpeg's audio decoders as LGPL (in mavio-deps), and PGS subtitles and SSA without its styling. It renders to a `SurfaceView` for HDR and low power, with tunneled playback where the TV supports it and frame rate matching with `Surface.setFrameRate`.
  * **libmpv**, the second, as mpv-android builds it, direct plays what Media3 does not, such as styled ASS subtitles and codecs without a hardware decoder, rendering with OpenGL ES into its own `SurfaceView` and decoding with MediaCodec where it can. A Media3 `SimpleBasePlayer` adapts it (`MpvPlayer`), so that the media session and the controller treat both engines alike. It is built from source with mpv-android's build scripts and its JNI layer (`is.xyz.mpv.MPVLib`) at pinned versions in mavio-deps, FFmpeg and mpv as GPL-3.0; libass draws with the system's fonts where a file embeds none.
* **What the phone, tablet and television apps leave out**, which Google Play does not accept or might not, as the iPhone and iPad app (§4.2): acquisition — the indexers and download clients, the quality profiles, custom formats and rules, Wanted, the download clients' queue, an item's acquisition and the indexer search (§6.3.11, §6.3.16–§6.3.18, §6.3.31) — the subtitles' settings, with searching the subtitle providers for an item (§6.3.12, §6.3.21), proxies and challenge solvers (§6.3.30), Discover's requests, plugins (§6.3.3), AI, with its providers and the assistant's settings, and the users' AI conversations (§6.3.13, §6.3.26); with them, Overview's plugin containers and Tasks (§6.3.7), whose tasks and jobs could not be shown whole without theirs. They open none of them in a browser either; the rest of the settings they have as the web UI does.

### 4.4 Desktop (`apps/desktop`)
* **Structure**: a Go app on MyGo for macOS, Windows and Linux, all of its windows native UI that MyGo draws on the GPU (Metal on macOS, Direct3D 11 on Windows, OpenGL on Linux); no web view. It builds with `CGO_ENABLED=0` like the server and ships with two shared libraries, libmpv and the core.
* **On the Mac**: a second Mac app beside `apps/macos`, which stays the Mac app built on the system's player and toolkit. The desktop app shares one code base with Windows and Linux, so that it is built and tried on a Mac; it is distributed as a notarized disk image outside the App Store, under an ID of its own (`dev.mavio.desktop`) and a name of its own, MavioGO (MyGo's `macos.name`), so that it is not taken for the Mac app; on Windows and Linux it is Mavio.
* **Icon**: the app icon (§6.2.1) — on macOS an Icon Composer document (`apps/desktop/icon/AppIcon.icon`) of the mark on white, or on black in the dark, elsewhere the light icon as a PNG — which `apps/desktop/scripts/icon.sh` makes from `libs/design/brand` on macOS.
* **Window and layout**: the desktop layout alone (§6.3), in a window of at least 1024 × 680, or television mode; the desktop type scale and macOS's control sizes (§6.1, §6.4). The sidebar and the settings' sidebar share one width, as the web UI's: the layout's by default, dragged by their edge or moved with the arrow keys between 200 and 400 px, restored by double-clicking it, and kept with the app's preferences. Each page the sidebar opens is a place keeping the pages opened from it, and a page opened from another has the round Back of glass, as the web UI's (§4.1). Videos play in a window of the player's of their own, one at a time, in place of what played; a setting of the playback opens a window for each video instead, so that several play at once. A window of the player's has no Back, closing as windows do, and its top drags it; on the Mac ⌘` and ⇧⌘` move between the app's windows. Television mode has the layout of [Television](tv.md): the tabs at the top in place of the sidebar, Libraries among them, focus moved by the arrow keys with Escape and Backspace going up a level, and videos playing in the app's window.
* **Sign-in**: the web UI's ([§4.1](#41-web-appsweb)), in a card on the wall of posters: a Mavio account signs in at mavio.dev in the browser, which comes back to a loopback address of the app (`http://127.0.0.1:<port>/callback`, with PKCE), or with a link code approved at mavio.dev/link, shown beside a QR code of the page with the code filled in; or the app connects to a server by its address, which signs in a standalone server's user with a password or Quick Connect, sends a server in mavio.dev mode back to the Mavio account's sign-in at its mavio.dev, and sends a new server to its setup in the browser. In television mode, turned on from the user menu or with ⌃⌘T (Shift+F11), and kept, the sign-in is the link code alone, at the television's sizes. The menu signs out of the Mavio account, or of the standalone server.
* **Core**: `libs/client-rust` through its C ABI, loaded at run time as MyGo loads native APIs — purego on macOS and Linux, the `syscall` package on Windows. Requests, results and events cross it as protobuf messages of the core's API, generated for Go. The screens the core does not model — a person, the whole cast and crew, an item's facts and extras, the settings — call the server's API as the web UI does, with `libs/proto`'s Connect clients for Go, whose HTTP transport sends each unary call through the core (`CallServer`): the core calls the server as the session, at the address it reaches it at, and answers with the response and that base URL, which the response's paths, such as the images' signed URLs, are relative to.
* **Player**: libmpv, loaded the same way and driven through its client API (commands, properties, and events read by a goroutine). mpv draws the video itself, in a native surface of its own placed under the surface MyGo draws the UI in. MyGo's video element places that surface: `Window.NewVideoView` makes a video view, whose native handle mpv takes as `wid`, and `ui.Video` shows it, making a hole through what the window paints where the video shows, so that the on-screen controller (§6.5), menus and dialogs, drawn by MyGo, show over the video; the pointer and the keyboard stay MyGo's over it. MyGo is used at the branch `v0.5.5-mavio` of its fork [mavioai/mygo](https://github.com/mavioai/mygo), which adds the video element to its release 0.5.5, pinned to a commit. mpv's video output waits for the main thread as it starts and as it stops, so the main thread never waits for mpv's core: the app sends its commands and properties asynchronously (`mpv_command_async`, `mpv_set_property_async`), reads the tracks on the goroutine that reads the events, and shuts mpv down off the main thread. libmpv is built without Lua, so mpv has no on-screen controller or scripts of its own.
  * **macOS**: mpv renders with `gpu-next` on Vulkan through MoltenVK (`gpu-context=macvk`) into a view of its own inside the video view, under MyGo's layer-backed view, decoding with VideoToolbox and outputting HDR through EDR (`target-colorspace-hint`). mpv's macOS output opens a window of its own; a patch of Mavio's, built into libmpv for macOS in mavio-deps (`mpv-macos`, a universal library for macOS 13 and later beside MoltenVK's), embeds it in the view `wid` names instead.
  * **Windows**: mpv renders into a child window (`wid`) with Direct3D 11 and `gpu-next`, outputting HDR10 with `target-colorspace-hint`; MyGo's frames are in the window's topmost DirectComposition target, above it.
  * **Linux**: mpv's OpenGL render API draws into a `GtkGLArea` under MyGo's surface in its `GtkOverlay`, on X11 and Wayland alike; HDR is tone mapped to SDR.
* **Playback**: the app declares as direct play every container and codec FFmpeg demuxes and mpv decodes, and HLS in fMP4 with H.264 or HEVC for what exceeds the quality chosen; mpv takes subtitles in the file and in files of their own (`sub-add`). The app selects the audio and subtitles the server chose by their indexes in the file (`ff-index`). The controller is the web UI's (§6.5) — the top bar, the scrubber, the side panel of audio and speed, subtitles and their offset, quality, and how the item plays — and a change of tracks or quality plays the item again where it is. Progress is reported each second and on pause, the playback stops where it is when the player closes or with no position when it ends, and the episodes after it in its season play in turn.
* **System integration**: Now Playing and the remote commands on macOS, System Media Transport Controls on Windows and MPRIS on Linux, which also bring the media keys; MyGo's power API keeps the display awake during playback.
* **Packaging and updates**: MyGo's — app bundles and notarized disk images, Windows installers, Debian packages and a Linux install script, code signing, and signed automatic updates with delta updates.

## 5. Shared Core (`libs/client-rust`)

### 5.1 Responsibilities
* **Servers and sign-in**: several servers signed in at once (§5.4), discovery, sign-in with a password or Quick Connect, and the sessions ([Accounts §5.2–§5.3](accounts.md#5-keys-and-tokens)): the device key and each server's session (its ID, access token and expiry) are kept by the app in the platform's secure storage (Keychain, Android Keystore, Windows Credential Manager, the Secret Service) through an interface the app implements — a development build of the desktop app, signed anew each build, keeps them in a file of its data directory instead, moving them there from the secure storage once — and the core's transport refreshes an access token by signing the server's nonce before it expires, or once the server rejects it.
* **Connect client**: [connect-rust](https://github.com/connectrpc/connect-rust) over HTTP/1.1 and HTTP/2, with the messages and clients generated from `libs/proto` into `libs/proto/gen/rust` and included by the crate `mavio-api`.
* **Event stream**: one `EventService` stream per server, reconnected with backoff, its events dispatched to the app.
* **Offline store**: SQLite (`rusqlite`, bundled SQLite) with the items last browsed, so that the app starts on cached content, the downloaded items, and the progress reports made offline, sent once the server is reachable.
* **Playback reporting**: starting playbacks, the periodic and final progress reports, and the replay of offline ones.
* **Downloads**: the queue, its state, and the items downloaded; the core asks the server for the file to keep, and the apps move its bytes with the platform's background transfer and report how far they got.
* **Screen state**: for every screen of §6.3 the data it shows — cards, rows, details, libraries and their grids, search results and downloads, as plain records with image URLs resolved — whether it came from the offline store, its errors, and the actions it offers. Home arrives through a listener as each server answers (§5.4). The apps keep each screen's loading state in their own observable model and only draw; the screens therefore behave alike on every platform. `libs/client-ts` gives the web UI the same data as hooks.
* **Assistant**: the fast path with `libs/intent` linked in, the client actions it carries out on the app's own player and screens, `Ask` and its events, voice sessions and their protocol, and the dialog state ([Assistant §3](assistant.md#3-a-request)); the apps bring the capture and playback of the microphone and speaker with the platform's echo cancellation ([Assistant §8.5](assistant.md#85-audio-and-echo)).

### 5.2 Boundaries
* No GUI, graphics or decoding: the view models hold state, not layout; the core never touches a video surface or a decoder, and never probes capabilities; the apps pass their `ClientCapabilities` in.
* An async API on Tokio; every call can be cancelled.
* Targets: `aarch64-apple-ios`, `aarch64-apple-ios-sim`, `aarch64-apple-tvos`, `aarch64-apple-tvos-sim`, `aarch64-apple-darwin`, `x86_64-apple-darwin`, `aarch64-linux-android`, `armv7-linux-androideabi` (many Android TV devices run 32-bit), `x86_64-linux-android`, `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`.

### 5.3 Bindings
* **The UniFFI API** (`mavio-uniffi`): the object `Client`, whose async functions run on one Tokio runtime of the process and are cancelled when the app drops their future; the interfaces the app implements: `SecureTokens` for the device key and the sessions, `CoreListener` for the streams' states and events, `HomeListener` for Home; and the client's capabilities as typed records, converted to `ClientCapabilities`.
* **Swift**: UniFFI generates the Swift API, packaged with the shared libraries as an XCFramework of dynamic frameworks that `MavioKit` depends on.
* **Kotlin**: UniFFI generates the Kotlin API, packaged with the shared libraries in the `core` module of `libs/android`.
* **Go**: a C ABI of three functions (`mavio-capi`, the library `maviocore`): `mavio_open` opens a client with the process's one callback and a context of the app's, `mavio_call` sends it a request with a call number of the app's choosing, and `mavio_close` closes it. Requests and answers are protobuf messages of `mavio.capi.v1`, defined in `libs/client-rust/proto`, in byte buffers; each answer, and every event of the servers under call number zero, comes back through the callback on the core's threads, so that purego creates a single callback for the process. A call answered in parts, Home's rows each time a server answers, sends messages marked `more` before its last; Quick Connect requests and playback sessions stay in the core, named to the app by numbers it passes back. `CallServer` forwards a unary call of the server's API, encoded as protobuf, as the session of a server signed in to, for the screens the core does not model. The core keeps no secrets of its own: the app gives it the device key and the sessions it keeps in the system's secure storage when it opens it, and stores the new and forgotten ones events tell it of. The Go binding is the Go module in `libs/client-rust/capi`, next to the C ABI: package `capi` loads the library without cgo, with purego on Linux and macOS and the `syscall` package on Windows, and turns each call into a function returning the answer, `Stream` giving a callback the parts of one answered in parts; its messages are generated for Go into `capi/gen`.

### 5.4 Several Servers
A client is signed in at once to every server of its sign-in ([Accounts §7](accounts.md#7-clients)) — a Mavio account's servers, its own and those of friends and family, or one standalone server — each with its own user and session. The servers do not know each other; the client alone puts them together, in the user's order of servers.
* **What spans servers**: Home, Search and Downloads. A library, an item's details and the player belong to one server, whose name the item shows when more than one server is signed in.
* **Home**, as Plex builds it: the hubs of every server (§6.3), merged:
  * **Continue Watching** is one hub across servers: the items being watched and the next episodes, by last activity;
  * **the same title on several servers**, matched by TMDB, TVDB or IMDb IDs, appears once: from the server where the user played it last, else the first in the user's order; its details offer the other servers' versions;
  * **the other hubs** follow server by server in the user's order, each server's in the order of its pinned libraries;
  * **Trending** from discovery appears once, from the first server that discovers, its titles marked available when any server has them; requests go to that server.
* **Search** asks every server at once and lists the results by server. A search runs when it is confirmed: the field of the sidebar, or of the Search page where no sidebar shows it, searches when Return is pressed, and typing alone does not leave the page. A server's row, titled From the Server with one server signed in and by its name with several, shows only once it answers with results, or as a line saying it cannot be reached; one spinner shows while nothing is drawn yet, and No Results once all have answered with nothing. Coming back from a result keeps the results without asking again, and confirming the same query again searches again. On the television, Search is a page of its own, with an on-screen keyboard beside the results ([Television §6.4](tv.md#64-search)).
* **Progressive and offline**: each server's hubs are drawn as they arrive, in their fixed places, so that a slow server holds back no other; Home is drawn at once from the offline store while every server is asked again, the hubs kept unmarked, and only an unreachable server's are marked offline.
* **Played state** stays on each server: the same title played on one server is not marked played on another.

## 6. Design System

The clients share one identity and one structure, and each looks native on its platform. Three layers divide the design:

| Layer | Rule | Contents |
| :--- | :--- | :--- |
| Shared | Defined once, the same everywhere | Tokens, content icons, the screens and their navigation, components, the on-screen controller, copy |
| Mapped | One concept, expressed the platform's way | The navigation container, the menu of more actions, the controls of settings |
| Platform | The platform's own | Window chrome, the menu bar, materials, system fonts, the back gesture, television focus, accessibility, system icons |

### 6.1 Design Tokens
Colors, typography, spacing, radii, elevation and motion are defined once in `libs/design/tokens` in the W3C Design Tokens (DTCG) format. Style Dictionary resolves them and `pnpm nx run design:generate` compiles them, with the icons and strings, into `libs/design/gen/{ts,swift,kotlin,go}`. The generated code is committed and CI checks that it is current, as with `libs/proto/gen`.
* **Color**: a dark theme, which suits artwork and dim rooms, and a light theme, both after Apple's system colors; both meet WCAG AA contrast, which the generator checks for every pair of text and background. The appearance follows the system unless the user chooses light or dark in settings; television starts dark, and the player is always dark. The primary button is filled with the label color; the accent, an orange taken from the logo, marks only progress, selection, links and switches.
* **Typography**: the type scales (sizes, weights, line heights) are shared, one per form factor: standard for phones and tablets, close to iOS's default sizes (body 16, callout 15); desktop, as on the Mac, with a body of 13 (callout 13, footnote 11), which the web UI takes with the desktop layout, as do the Mac and desktop apps; and television's ([Television](tv.md)); the family is the platform's system font — SF Pro on Apple platforms, Roboto on Android, Segoe UI Variable on Windows, and Inter, shipped with the app, on Linux and the web — so that Dynamic Type and font scaling apply. There is no brand typeface: titles, including those over artwork, are the system font in bold, white over a dark scrim on artwork; the logo is drawn rather than set (§6.2.1).
* **Sizes per form factor**: the tokens have phone, tablet, desktop and television values (television sized for 10-foot viewing and overscan-safe margins).

### 6.2 Icons
Content and brand icons are [Phosphor](https://phosphoricons.com/) (MIT), pinned in `libs/design/icons/icons.json`, which maps semantic names to Phosphor names; the generator copies their SVG sources into `libs/design/icons/svg` and compiles them into path data for the web UI and for MyGo, which draws them itself, asset catalog images and Android vector drawables. Regular and Fill weights mark inactive and active states (favorite, mute, loop, subtitles) without shifting the layout. The logos of the AI providers pi-ai reaches are kept as SVG sources in `libs/design/providers`, from [lobehub/icons](https://github.com/lobehub/icons) (MIT), with `providers.json` mapping each provider's ID to one; those named `-color` keep their colors and the others draw in the text's color. The generator writes them for every client — SVG text for the web UI, MyGo and the Android apps, an asset catalog for the Apple apps — each looked up by the provider's ID. System controls use the platform's icons — SF Symbols on Apple platforms (share, AirPlay, Picture in Picture, menus) and Material Symbols on Android — where users expect them.

#### 6.2.1 Logo
The logo has two forms, kept as SVG sources in `libs/design/brand`, and the two never appear together:
* **Mark**: an uppercase M folded like a ribbon — two stems behind, and two diagonals in front that shade the stems where they cross them — drawn on a grid of 64 units with stems and diagonals 16 wide (`mark.svg`). It is the app icon, on a white background (`app-icon-light.svg`) or a black one (`app-icon-dark.svg`), and replaces the wordmark where that would be narrower than 64 px.
* **Wordmark**: "Mavio" drawn from straight strokes 12 wide and 45° cuts, with a cap height of 64 and an x-height of 44 (`wordmark.svg`); in a single color, white or black, only where a gradient cannot be drawn (`wordmark-white.svg`, `wordmark-black.svg`).
* **Color**: a gradient from yellow `#FFD34E` through orange `#FF9A2E` to red `#F0412F`, running from the top left to the bottom right.

### 6.3 Information Architecture
Every client has the same screens with the same names, reached the same way:
* **Top-level destinations**: Home (§6.3.1), the libraries, Discover (§6.3.2), Search, Downloads (the apps), and the settings.
* **Screens below them**: a library (grid with sort and filters, narrowed to a genre, keyword or studio when opened from an item's details), an item's details (movie, series, season, collection) and its whole cast and crew, a person (§6.3.19), a discovered title and a catalog (§6.3.2), the player, the account (`/settings/account`), opened from the user's card at the top of the settings, with its credentials and the servers in their order, each with the address it gives others — the best of the URLs it published, which is the one copied — and, where it differs, the one this device reaches it at, such as localhost; and settings, in three groups: Advanced, the advanced tools, for the administrators of a server — the indexer search (§6.3.31) and the AI conversations of the server chosen (§6.3.26); This Device; and the Server, the settings of one server — the devices signed in to it as the user and the issues reported and, for its administrators, the rest, in the order a server is set up and kept — overview (§6.3.6), general settings (§6.3.8), users (§6.3.5) and devices (§6.3.15); the menus Media, with libraries (§6.3.4), storage (§6.3.10) and transcoding (§6.3.9), and Acquisition & Downloads, with acquisition (§6.3.11), wanted (§6.3.16), downloads (§6.3.17) and subtitles (§6.3.12); AI (§6.3.13), plugins (§6.3.3) and proxies (§6.3.30); and the menu Monitoring & Maintenance, with activity (§6.3.6), issues, tasks (§6.3.7), logs, backups (§6.3.14) and API keys (§6.3.15) — each menu a second level of its own. The desktop layout opens a menu in place in the settings' sidebar, open while it holds the section shown, except in the desktop app, whose settings' sidebar lists each menu flat as a group of its own after the Server's; the phone and the television open it as a list of its own, between the settings' list and its sections. Beside the sidebar a section is centered in the space left, at most 900 px wide. A menu left with one section for the user, as Monitoring & Maintenance with the issues alone for a user who does not administer the server, is that section, and one left with none is not shown. With a Mavio account a picker above the Server group, as wide as its rows, chooses among the servers signed in to, the server serving the web UI marked; where no sidebar shows the settings, the title line of a Server section or menu ends with it, small and quiet; a standalone server's user, signed in to one server, has none. Above a page's title a trail of links leads back up: on the phone, Settings, its menu and, below a section, the section, as Settings › Media › Libraries above a library; where the sidebar shows the settings, it shows only the menu and section above a page below a section. A section's title line holds nothing else: its actions are where what they act on is — adding is the last row of the list added to (Add Library, Add User, Add Remote, Add Proxy), and a page's own, such as a library's Scan or Delete, follow its fields. The Android apps end the settings with About, after the Server group: the app — its name as the servers know it, the client's and the core's versions ([Development §7](development.md#7-releases-and-versioning)) and its license — and the device — its name and ID as the servers know them, its manufacturer, model, system version and architecture.
* **Navigation container**: three layouts, chosen by the form factor rather than the platform, so that each is the same on every platform that uses it. Between the phone and desktop layouts the width of the window decides, with the breakpoints of Android's window size classes, the same in the apps and the web UI: compact (under 600), medium (600 to 840) and expanded (840 and over):
  * **Phone**: in compact width — iPhone, Android phones, tablets in split screen and the web UI in a phone's browser — a tab bar at the bottom with Home, the libraries and Discover, shown on the places alone and hidden on a page opened from one; the header at the top is clear, as iOS's: it holds the wordmark, or Back on a page opened from another, and at its right, on the places alone, as the tab bar, a bare Search and the avatar on a circle of the tab bar's glass without an edge, which opens the settings, where the apps keep Downloads under This Device; a hero reaches the top under it, its buttons white over the hero, and once the page scrolls under it, glass fading out downward keeps them readable. The iPad, at every width, reaches the same destinations the same way, in the system's tab bar at the top, with Search at its end and hidden on a page opened from a place, and the avatar at the header's right. From iOS 26 the iPhone's header, as the iPad's, is clear, its buttons of Liquid Glass — the avatar on the regular glass of the iPad's beside a bare Search — and a hero reaches the top under it. On a touch screen a page that reads what can change is read again by pulling it down, keeping what it shows until the answer arrives: Home, the libraries, a library's tabs, an item's details, its cast and crew, a person, Discover, a catalog, a discovered title, person or collection, and the Server sections that list or report — overview, users, devices, libraries, storage, activity, tasks, logs, backups, issues and API keys; forms, Search and the player are not.
  * **Desktop**: in medium and expanded width — the web UI, the Mac, desktops and Android tablets — a sidebar on the left with Search, Home, Discover, Downloads (in the apps), Features — the advanced tools pinned (§6.3.31), shown only when one is — and the libraries, which collapses to a rail of icons; in medium width, such as a tablet in portrait, it starts collapsed and opens over the content. Its foot holds the signed-in user's avatar and name, which open a menu: the appearance (system, light or dark) beside the name, switching users ([Accounts](accounts.md) §3.6, §4.4), settings, switching to television mode, sign-ins, managing the account on mavio.dev or the server, and signing out. Where a keyboard is at hand — the web UI on a computer, the Mac and the desktop app — the menu shows the shortcuts of its items, each platform's own: the settings with ⌘, (Ctrl+, elsewhere), television mode with ⌃⌘T (Shift+F11), and full screen with the browser's and the Mac's keys, ⌃⌘F (F11); phones, tablets and televisions show none, having no keyboard to press them.
  * **Television**: on Apple TV, Android TV and Google TV, and in the television mode of the web UI, the Mac and the desktop app (a setting under Appearance, for a computer connected to a TV): a navigation bar at the top with Home, the libraries, Discover and Search, a button of three dots at the right for the same menu, and focus moved by the remote alone. It is specified in [Television](tv.md).

#### 6.3.1 Home
Home is a column of hubs, after Plex's: rows of items, each a reason to watch something.
* **Hubs**: Continue Watching and the requests that became available first, then for each pinned library its hubs — Recently Added, Recently Released, Recently Aired (episodes), Top Rated, Top Unplayed, Start Watching (series not begun), Rediscover (played long ago), Because You Watched, Because You Like, More in a genre, Starring, Directed by, and the collections an administrator promoted — and Trending, the titles discovery offers that no server has, to request.
* **Who chooses**: administrators choose for each library which hubs appear on its Recommended tab and which on Home; each user pins and orders libraries, which orders their hubs, and hides hubs. Continue Watching cannot be hidden.
* **Rotation**: the hubs seeded by an item, a genre or a person (Because You Watched, More in, Starring, Directed by) draw their seeds from what the user played recently, chosen anew each day, so that Home changes from day to day and stays put during a day.
* **Library tabs**: a library opens on its Recommended tab, its hubs, beside the grid of all its items.
* **Hero**: Home opens with up to five of the latest films and shows with backdrops, one after another, each with its facts and the buttons to play it and open its details.

#### 6.3.2 Discover
Discover finds films and shows to request, after Seerr, from the discovery catalogs of the server's metadata providers ([Plugins](plugins.md)).
* **Where**: Discover asks the first signed-in server whose providers offer catalogs; it is a destination only where one does.
* **Rows**: Trending, then Popular, Upcoming and Top Rated, each of movies and of series, and the lists the providers offer; each row opens its catalog, a grid loaded page by page. Titles and overviews come in the language of the client.
* **Cards**: a title's card marks it once available on the server and while requested or being acquired.
* **A title**, in the client's language as the catalogs: laid out as Seerr's page: its backdrop and poster, under its name the year, rating, runtime and genres, with Trailer opening its trailer on the web; then beside each other its tagline, overview, the six leading crew with View Full Crew opening the Credits Screen with the crew alone, and its keywords, and a movie's collection opening the collection's page, its Rotten Tomatoes critics' and audience scores, fresh or rotten, IMDb rating and TMDB score, each opening its page, original title when in another language, production status, theatrical, digital and physical releases, first, last and next air dates, runtime, revenue and budget, original language, countries with their flags, studios or networks, the services streaming it in the server's country, and, as Seerr's, the logos linking it on TMDB, TVDB (series), IMDb, Rotten Tomatoes, Trakt, Simkl and Letterboxd (movies), after Mavio's opening its item when the server has it; a genre, keyword, language, studio or network opens the popular titles of it; below its seasons the first twenty of its cast; Watch opens the item when the server has it, and Request asks for it, for a series with the seasons to request, all of those not requested yet by default. A series lists its seasons as Seerr does, each in its own bordered box, the latest first and specials last, with what the server has of each, a season expanding to its episodes with their names, air dates, overviews and stills; Recommendations and Similar follow. Home's Trending opens a title no server has here. As on Seerr, administrators approve or decline its pending requests in place and see how far its downloads have come by its status, and Manage opens its requests, downloads and open issues, blocklists it when nothing of it is requested or had, and takes it off the blocklist; Report Issue reports a problem with what the library has of it.
* **A person**, opened from the cast and crew of a title when they are not of the server, as Seerr's: their photo, birth and death, place of birth, other names, the logos linking them on TMDB and IMDb and biography, then the movies and series they play in and work on as title cards with their roles and what the server has of each, the most voted first and the department they are known for first, all, movies or series.
* **A collection**, as Seerr's: its backdrop, poster, number of movies, what the server has of them and overview; Request Collection chooses the movies to request, all those not requested yet by default, and administrators blocklist its movies or take them off the blocklist; then its movies in release order as title cards.
* **Requests**: opened from Discover's title, the server's requests, newest first and page by page, all or those pending, approved, available, failed or declined — the user's own, with what is left of their quotas, or everyone's for its administrators. A request shows its title's poster, its kind and seasons, who asked and when, its status and why it failed. Administrators approve and decline pending requests and retry failed ones; the seasons of a pending series request are changed in the dialog that requested them; pending requests are deleted by their user, and any by administrators, after confirming.

#### 6.3.3 Plugins
Plugins, in the settings' Server group, shown to the administrators of the server chosen, follow Jellyfin's plugin pages ([Plugins](plugins.md)).
* **List**: two tabs of cards, Available, every plugin the server's catalogs offer, installed or not, and Installed; a card shows the plugin's category, name, description and its version or state, and marks an update. Beside the tabs a picker shows one category, among those of the tab's plugins, and Manage Catalogs opens the catalogs. A catalog that cannot be reached is reported on Available.
* **A plugin**: opened from its card, its trail leading back to the list as it was left: its description; its state, version, the newest version, category, author, license, website, catalog and the hosts it may reach; for a WASM plugin reaching hosts and for a process plugin, Network, with the proxy its requests go through, saved as it is chosen, asking first when a process plugin changes between direct and proxied, which restarts it; Install, or Update to the newest version, a switch enabling and disabling it, unavailable while the plugin starts or stops, its tooltip saying so, and Uninstall, which asks to confirm first; and the versions its catalog offers, each with its release date and changes, to install another.
* **Language**: the web UI asks servers for its language in every call's `Accept-Language`, and plugins' names, descriptions, tasks and configuration forms come in it where the plugin is translated ([Architecture §7.5](architecture.md#75-plugins-in-the-server)).
* **Configuration**: on an installed plugin's page, a form built from its manifest's schema — text, secrets with a button revealing them, numbers, switches, choices, choices of several — checkboxes, or for more than eight options tags in their order, each removed by its button and others added from a picker searching them — lists one item per line, optional groups behind a switch, and lists of groups to add and remove — saved with the server's validation reported; a plugin with its own settings page also links to it. Properties the server generates are not shown. A switch needing a container dependency not set up, as a solver's Enabled while its FlareSolverr is not, is off and cannot be turned on, telling to set the dependency up below. A property whose options the server lists is chosen by typing into a field whose popup lists the options by name, one compact row each with its description, language and its protocol and privacy as badges, under filters by protocol and privacy and the count of the options matching; choosing one draws the settings it takes, and names the group after it while the group bears the previous option's name or none.
* **Container dependencies**: on an installed plugin's page, each dependency its manifest declares, with its description and state, how it runs (not set, run by the server, or at an address), whether a GPU is used, for one run by the server, the proxy it reaches sites through, unless it reaches them directly (`direct`), asking first when it changes between direct and proxied, which recreates the container, and the `docker run` command equivalent to how it runs, shown when asked; and, at an address, the address and the `docker run` and Compose commands that run it, with and without a GPU; the list refreshes while dependencies start.
* **Catalogs**: the addresses of the plugin catalogs, to add and remove, its trail leading back to the list.

#### 6.3.4 Libraries
Libraries, in the settings' Server group, shown to the administrators of the server chosen, list the server's libraries, those of collections and playlists aside.
* **List**: each library with its kind, the number of its folders and Scan, which reports whether a scan started or one was already waiting; while a library is being scanned its row shows what the scan is doing, reading folders or analyzing media, with how many of how many, and a bar of how far it has come, then Scan finished; Add Library opens an empty library's page.
* **A library**: its name and kind; its folders, added by path, `rclone:<remote>:<path>` included, or chosen by walking the server's folders, each with its storage class, Automatic showing the one detected; the language and country of its metadata, named in the UI's language, or the server's; saving metadata beside the media and, by kind, collections of movies and lyrics; scanning automatically, never or every hour, 6 or 12 hours, day or week, and by kind seek thumbnails, chapter images and loudness; for shows, the missing episodes listed, aired or upcoming, with specials, kept a number of days; Save, Scan, and Delete, which asks to confirm first. What the page does not show of a library, its providers and hubs, is kept as it is.

#### 6.3.5 Users
Users, in the settings' Server group, shown to the administrators of the server chosen, list the server's users, the administrator first, each with its badges (administrator, managed, disabled) and when it last signed in.
* **Adding**: a member with a name and a password, or a managed user with a name, an optional four-digit PIN and a restriction profile ([Accounts](accounts.md) §4.1).
* **A user**: its name, whether it is disabled and, for a managed user, its restriction profile; its access — all libraries or those checked, the highest rating, named by the age it stands for, hiding unrated items, the labels it may only see and those hidden, and downloads; its playback — transcoding, a streaming limit and the number of simultaneous streams; what it may request, approved at once or not, with its own quotas or the server's, and reporting issues; Save, and Delete, which asks to confirm first. Its sign-ins below take effect at once: setting a password, which makes a managed user a member, the administrator's own being changed in its account's settings; a managed user's PIN; a link that converts a managed user, valid for 7 days; turning off its authenticator; and deleting its passkeys.
* **Invitation links**: making a link with a number of uses (1 to 100), the days it is valid (1 to 30) and the access it gives, shown once with a button to copy it, and the links not used up, to revoke, those of managed users apart. A link is the address of the server's web UI `/invite#<token>`: the token is in the fragment, so it is never sent in a request. Opening it shows the invitation screen, which takes a name, unless the link converts a managed user, and a password or a passkey, and signs in as the member made; a link expired, used up or revoked says so.
* **mavio.dev mode**: the users are the Mavio accounts with access to the server. Their names, access and whether they are disabled are mavio.dev's and shown read-only; only playback and requests are the server's; there is no adding, no invitations and no sign-ins, and a user can be deleted only once its access was revoked.

#### 6.3.6 Overview and Activity
Overview, first in the settings' Server group, and Activity after it, shown to the administrators of the server chosen. Overview:
* **Server**: whether it serves, its version, the operating system and architecture it runs on, its database, its FFmpeg, the container engine it runs containers on — its name, version, API version, whether rootless and, under them, its endpoint, or why there is none — and how long it has been running.
* **Load**: a card each of the server's computer's CPU — busy share, user, system and the server's own — memory — used of the total, Normal or High from 90% used, available, swap and the server's own — disks — the space available of the computer's own disks together, shares and cloud drives aside and the volumes of one container counted once, read and write rates and the bytes written since the computer started — and network — download and upload rates, the loopback, tunnels and on Linux virtual interfaces aside, and the bytes received and sent — each with a dotted graph of the last two minutes. The server samples them every two seconds while the page asks, and stops once it has not for a while; a part the operating system does not tell says so.
* **Containers**: the container dependencies of the plugins that are set, each with the plugin it is for, its state, or the address it is reached at, and the `docker run` command it runs as, shown when asked; refreshed every few seconds.

Activity:
* **Now playing**: every device playing, refreshed every few seconds — the item, the user, the device and client, whether it plays directly, streams directly or transcodes, and how far it is, paused or not.
* **Recent activity**: what happened on the server, newest first, each with its severity and when, shown all or only warnings and errors or only errors, with more on request.

#### 6.3.7 Tasks
Tasks, last in the settings' Server group, shown to the administrators of the server chosen:
* **Tasks**: the server's recurring tasks and, apart, its plugins', each with its description, how its last run went and when, how often it runs or that it runs on demand, when it runs next and the error of a failed run; Run queues a run now, saying whether one was already queued, and a running task says so, refreshed every few seconds while it runs.
* **Jobs**: the jobs of the server's queue, newest first, all or only those waiting and running, failed or succeeded, each with its kind, state, when it runs or ran, its attempt when retried and its error, with more on request.

#### 6.3.8 General
General, in the settings' Server group, shown to the administrators of the server chosen: the server's name, which clients take at once, empty for the computer's; the language and country of metadata for libraries without their own, requests and Discover; how many days a device stays signed in unused; on a standalone server, the plugin that sends the PINs of forgotten passwords, among those able to, or none; and the network — the base URL behind a reverse proxy, the HTTPS port with the paths of a PEM certificate and key, or in mavio.dev mode the server's mavio.site certificate, discovery on the local network and, in mavio.dev mode, the relay. Save applies them at once.

#### 6.3.9 Transcoding
Transcoding, in the settings' Server group, shown to the administrators of the server chosen: the hardware acceleration, among those the server's FFmpeg supports, and hardware encoding; the encoder's preset, by the source or chosen, the quality of H.264 and HEVC as CRF and the number of threads; tone mapping of HDR with its algorithm, range, desaturation and peak, deinterlacing with its filter and double frame rate, and cropping black borders; the boost of audio downmixed to stereo; and the folder of running transcodes. Save applies them at once.

#### 6.3.10 Storage
Storage, in the settings' Server group, shown to the administrators of the server chosen: the disks of the server's computer, on Linux, macOS and Windows — its drives and the shares and cloud drives mounted on it, neither the system's own file systems nor, on macOS, disk images mounted read-only — each with its label or path, its kind and file system, and a bar of how much of it is used, orange from 85% and red from 95%, a disk that does not answer in two seconds told so; the remotes, each with its kind, a dot, green when the server lists its root and red, with the error, when it cannot, as when a login expired, and how much of it is used where its backend tells, as 115's does; whether the server reaches rclone, its version, and whether the server runs it or reaches one run elsewhere; and the offline download clients. Adding a remote takes its name, its kind among rclone's backends and the kind's settings — those its provider takes, the rarely changed behind a switch, each with rclone's help, a choice where rclone lists the values and a hidden field for secrets — and then asks the questions its configuration has left, one at a time until none is left: each under rclone's words, a yes or no answered with its buttons, a choice or a value, such as the token of authorizing a cloud drive, with Continue. A question drawing a QR code, as 115's login asks, shows it as an image to scan and is answered again until the phone confirms the login. Cancelling, once no answer is being sent, deletes a new remote and leaves an existing one as its answers left it. A remote's page changes its settings, secrets left empty keeping theirs, configures it again, its questions then taking the page, as a login that expired is renewed, walks its folders, which shows that the server reaches it, and deletes it. An offline download client is a cloud drive downloading magnet links itself, edited in place: its name, its folder on a remote, its tags and priority, whether it is on, and whether imported and failed downloads leave the drive's list. The libraries' folder picker (§6.3.4) lists the remotes beside the server's disks and walks their folders.

#### 6.3.11 Acquisition
Acquisition, in the settings' Server group, shown to the administrators of the server chosen: the indexers and the download clients the server's plugins have configured, each with its plugin, protocol and priority, whether it is off or left out after failures and until when, and a link to its plugin's settings (§6.3.3); the quality profiles of movies and of series; and pages for the rest of what decides which releases are grabbed. A quality profile has its name, whether upgrades are allowed and the quality where they stop, the language a movie's release must have, its qualities best first, each turned on or off and moved up or down, the score of each custom format, and the lowest score, the score where upgrades stop and the least an upgrade must add; a new profile starts from the kind's qualities. The quality definitions page sets each quality's sizes per kind. A custom format is a name and its conditions — a release title or group pattern, a source, resolution, modifier, language, indexer flag or release type chosen from those the server knows, a size or year range — each negated or required. Delay profiles are listed in the order they apply, the default last, each with its protocols, the one preferred, the delay of each and its tags, and are moved up and down; release profiles require or ignore words or patterns, for an indexer or all of them and the titles of their tags; remote path mappings turn a download client host's folder into the server's.

#### 6.3.12 Subtitles
Subtitles, in the settings' Server group, shown to the administrators of the server chosen: the providers of the subtitle provider plugins, each with its plugin, whether it serves movies or episodes, and whether it is off or paused after failures and until when; the translators of the subtitle translator plugins; both linking to their plugin's settings (§6.3.3); the subtitle profiles; each library with the profile assigned to it, chosen in place; and the pages of the settings. A subtitle profile has its name, its languages — each with whether hearing-impaired subtitles are accepted, required or excluded, whether only forced subtitles are wanted, and whether the language is wanted only when the audio has it or not when it does — the language whose subtitles end the search, whether subtitles keep their provider's format, the tag that assigns it, and the words subtitle names must and must not contain. Searching and saving holds the minimum scores, how often wanted subtitles are searched and whether failing ones are searched less often, release names and hashing, the embedded streams counted and the languages of streams without one, upgrades, where subtitles are saved and how they are named, the fixes applied to downloads, the languages counted as others and whether tags assign profiles. Synchronization holds whether downloads are aligned with the audio, below which scores, and the bounds of the alignment. Translation holds the translator — a plugin's or a model of a signed-in AI provider (§6.3.13) — and its fallbacks in order, the score and credit of translations, how cues are formatted, the context, batches and prompts of AI models, retries, the validation of subtitles before translating, and the automatic translation of subtitles still missing, from the source languages in order.

#### 6.3.13 AI

AI, in the settings' Server group, shown to the administrators of the server chosen: first the assistant's settings, then the providers of the AI gateway plugin added — those with a credential, each with where it comes from: an API key, an account signed in, or one the plugin found in its environment — and their numbers of models, the list ending in Add Provider, a button choosing among the others, its popup as wide as the row finding them by typing their names, which opens the provider chosen; without an AI gateway plugin, a link to Plugins (§6.3.3) instead of the providers. A provider's page holds its sign-in with an account, its API key and its models, the list scrolling within its group. A sign-in runs on the server and is followed as it goes: the pages to open, each in a new tab, its address on one line cut to fit with a button copying it, the codes to enter, its progress and the questions it asks — a choice, a text, a secret, or the address a sign-in page redirected to — each answered in place, until it succeeds, fails or is canceled. A sign-in with a subscription meant for the provider's own apps carries a warning that using it from a server may break the provider's terms, and the choice is left to the administrator. An API key is stored and never shown again; a stored key or account is removed after confirming. Each model shows its context window, whether it reasons and reads images, and its cost per million tokens. Above the providers, with or without a gateway, are the assistant's settings ([Assistant §10](assistant.md#10-settings-and-privacy)): whether it is on, its model among the signed-in providers' or none for simple commands only — a button whose popup, as wide as the row, searches the models in a virtual list, each on two lines: its provider's logo, its name and, smaller and quieter, its provider's, then, smaller and quieter too, its details — code mode, who may use the AI path, the idle time and retention of conversations, memory, and, with a `VOICE_SESSION` plugin, the recognizer and voice of each language, hints, a turn's longest pause, the commit delay and a voice session's idle time, saved together.

The assistant's settings come before the providers ([Assistant §10](assistant.md#10-settings-and-privacy)): whether it is on, its model and code mode, the users who may use the AI path, conversations' idle time and retention, memory, and the voice plugin's recognizers and voices by language with the turn settings.

#### 6.3.14 Backups and logs

Backups and Logs, in the settings' Server group, shown to the administrators of the server chosen. Backups makes a backup of the server now and lists its backups, newest first, each with when it was made, its size and the server version that made it, downloaded or deleted after confirming; a backup is downloaded with the session's access token, which a link cannot send, so its file is read whole before it is saved, and it is restored by starting a new server with it. Logs shows the server's recent log records, newest first, each with its time, level, message and attributes, from a minimum level, over the last hour, the last day or all those kept, filtered by words and refreshed on demand.

#### 6.3.15 API keys

A key is made with a name; its token is shown once, to copy, and hidden when the key is revoked.
#### 6.3.16 Wanted
Wanted, in the settings' Server group, shown to the administrators of the server chosen: the monitored movies or episodes missing a file, or whose file is below their quality profile's cutoff, each linking to its details with what it shows — the quality of its file, an episode's air date and absolute number, whether a movie is not yet available — searched for or unmonitored in place; a search of everything listed, and an RSS sync of the indexers' recent releases.

#### 6.3.17 Downloads
Downloads, in the settings' Server group, shown to the administrators of the server chosen, in four tabs. The blocklist holds the releases not to grab again, each removed in place. The manual import lists the video files of a folder on the server and imports those matched to a wanted movie.
#### 6.3.18 An item's acquisition
On the details of a movie, series, season or episode, the administrators of its server find its acquisition below its details. A wanted movie or series has whether it is monitored, its quality profile, when it was last searched for, an automatic search and an interactive one; a season or an episode has whether it is monitored and the two searches; a movie not wanted has only the interactive search. The interactive search lists the releases the indexers have of the item, the rejected last, each with its quality, languages, size, age, seeders and peers or Usenet, indexer, custom formats and score, and rejections, grabbed in place; the indexers that failed are named above them. The item's downloads and latest events follow, as in Downloads (§6.3.17).
#### 6.3.19 Person
A person's page, opened from the cast and crew on an item's details: their photo, or the placeholder of missing artwork without one, their name, birth date and age, birthplace and death date, their biography shortened until asked for more, and the links of their external IDs; under them the movies, series and episodes of the server crediting them, newest first.
#### 6.3.20 Playlists and collections
An item's actions end with More, a menu adding the item to one of the user's playlists or a new one — a series, season or album adding its playable items — and, for the server's administrators, to a collection or a new one; on a playlist, and on a collection for administrators, it renames or deletes it, the deletion returning to its library. A playlist's details list its entries in order, the same item possibly several times, each played, moved up or down, or removed in place. A collection's details show its members in the order they were added, which its administrators remove after Edit.

#### 6.3.21 An item's subtitles
A movie's or episode's details show its server's administrators its subtitles after its acquisition: the subtitle profile it uses and the languages it lacks, and the subtitles it has, each labelled with its language — forced or for the hearing impaired — and its file or embedded stream, and marked when the profile does not count it. A subtitle file is synchronized against the audio or another subtitle, showing the offset and speed ratio applied, modified with the subtitle settings' modifications, translated into a language by the default translator, a plugin translator or an AI model, the translation running as a job, or deleted after confirmation; an embedded subtitle is extracted into a file or translated. Search opens a dialog listing the providers' subtitles in the languages the profile lacks, or in a chosen language — the user's own when nothing is lacking — each with its release names, match and unmatched properties, provider, uploader and format, and downloaded in place; providers that failed are named. Upload sends an SRT, ASS, SSA, VTT or SUB file in a chosen language, forced or for the hearing impaired.

#### 6.3.22 An item's metadata
For the server's administrators, an item's More menu (§6.3.20) also edits its metadata, identifies it, refreshes it and edits its images; a playlist has none of them, a collection is not refreshed, and only the kinds the providers know — movies, series, music artists, albums and videos, books and audiobooks — are identified. Edit Metadata opens a form of the fields the item's kind has — its names, overview and tagline, numbers, dates, series status, runtime, ratings, artists, genres, tags, studios and production locations, the latter several separated by commas — its external IDs, one for each kind of ID its kind carries, and its locks: all of its metadata, or names, overview, genres, tags, studios, production locations, parental rating, runtime and cast one by one; saving sends only the fields changed. Refresh reads the item's files and the providers again, keeping what it has, or replaces all of its metadata. Edit Images shows the item's images of a kind — primary, backdrop, logo, thumbnail, banner, art or disc — each deleted after confirmation, and the providers' images of the kind with their size and language, one chosen to replace the first; an image file is uploaded instead.

#### 6.3.23 Remote control
A playable item's More menu begins with Play On, listing the user's other online devices — their own sessions and the plugins' remote devices, each with what it plays — and playing the item on the chosen one from its resume position, then controlling it. The Devices settings open the same control for any online device other than the browser itself. The control shows what the device plays with its position, seeks by the slider or ten seconds back and forward, plays and pauses, goes to the previous or next item, stops, mutes or sets the volume, and sends a message to show. The browser follows its servers' events and carries out the commands sent to it: Play opens the player on the first item at its position, a message shows over any screen until dismissed or for its timeout, and the player pauses, resumes, stops, seeks, goes to the next or previous item and sets its volume.


#### 6.3.24 SyncPlay
A playable item's More menu also opens Watch Together: outside a group it lists the server's groups the user may join, with their members, and creates one, named after the user at first; in a group it shows what the group does — nothing, playing or paused, or the members it waits for — and its members, plays the item in the group from its resume position, returns to the group's playback, and leaves the group. While the browser is in a group, the screens show its indicator, opening the same dialog. When the group waits for the browser — it set a queue, moved to another entry, seeked, or the browser joined while it played — the browser opens the player on the group's entry at its position. There the player follows the group: it waits paused at the group's position and reports when it can play, carries out the group's commands at their time by the server's clock, which it measures as in NTP every half minute along with the round trip it reports, catches up when the command's time has passed, follows the group's state when an update brings no command, as the group sent again when its stream reopens, and keeps up with the group by playing up to ten percent faster or slower, or skipping when more than two seconds away; buffering while the group plays makes the group wait. Its play, pause, seek, next and remote controls ask the group instead, its speed is fixed, its chip names the group or the members it waits for, and at the end of an entry the group's first member moves the group on to the next entry, or stops it after the last.

#### 6.3.25 Issues
Users allowed to report issues, and administrators, report a problem with a movie, series, season or episode from its More menu: its kind — video, audio, subtitles or other — for a series the season and episode, 0 for all, and what is wrong, after which the issue opens. #### 6.3.30 Proxies

#### 6.3.31 Indexer Search
The indexer search, in the settings' Advanced group, shown to users who administer a server, searches the indexers by text, as Prowlarr's search does: a query, with a Mavio account the servers to search, the type (anything, movies or TV), a Newznab top category and, for one server, one of its enabled indexers (`SearchReleases`). Its releases are a table, as Prowlarr's — protocol, age, title, indexer, size, grabs, seeders and peers, categories — sorted by a column's heading, the title at least 320 px wide and the table scrolling sideways where it does not fit, and each is sent to a download client, its magnet link copied, for a torrent client of the user's own, or its page on the indexer opened in a window of its own. Sending one (`GrabRelease` without an item) gives it to the client chosen as an item's grab would be, by the protocol and the indexer's client, in the client's category for series when its categories are television's and for movies otherwise; the download is the client's alone, neither tracked nor imported. On a phone each release is a row of its title over the rest. With a Mavio account a picker after the query chooses among the servers the user administers, All Servers first and the default: All searches every server at once, each server's releases a group named by the server with their count, the indexers that failed and pages of their own of 50; a server chosen searches it alone. A standalone server's user searches the one server. The tool's row in the settings' sidebar ends with a pin, an icon alone, shown while the tool is pinned or the row pointed at: a pinned tool is listed in the sidebar's Features group, in the order pinned, and opens in the app's layout (`/tools/<tool>`); pins are the browser's, and the Features group is not shown with none.

### 6.4 Components
The core components are specified once in `libs/design/components.md` — their anatomy, their states (default, focused, pressed, loading, watched progress, played), their sizes per form factor and their tokens — and implemented natively on each platform; the specification is shared, not the code. They are the poster and thumbnail cards, the shelf row, the details header and screen, the episode card and row, the person card, the track and subtitle pickers, the empty, error and offline states, and the assistant's orb and cards. Television adds the focused state (scale and shadow) to every card. The controls follow each platform's own: SwiftUI's and Compose's on the native apps, and on the web those `src/controls` draws (§4.1) in the shapes of Apple's — popups of glass, green switches, segmented controls. Their sizes follow the type scale's: the phone's below the desktop width — buttons 36 px tall, as tall as its selects, and the television's 44 — and from it, outside TV mode, macOS's regular controls — buttons 28 px tall with 12 px at their sides, fields and selects 28 px tall, a switch of 38 × 22, a checkbox of 16 and menu items of 28.

### 6.5 On-Screen Controller
Every player follows one layout and state machine:
* **Top bar**: title, season and episode, and the cast or AirPlay action.
* **Center**: play and pause; on touch screens double tap to seek, vertical swipes for brightness and volume, long press for double speed.
* **Bottom bar**: elapsed and remaining time, a seek bar with chapter marks and trickplay thumbnails, audio and subtitle selection with subtitle offset, playback speed, and full screen and Picture in Picture. The audio, subtitles, quality and how the item plays are in a side panel. The quality caps the bitrate the server sends: Original 200 Mbit/s, 1080p 10, 720p 4 and 480p 1.5; Auto, the default, allows 100 Mbit/s from a server on the local network — an address that is loopback, private or link-local, a `localhost` or `.local` name, or a mavio.site name of such an address — and 40 Mbit/s otherwise, where an upload or the relay sets the pace. An episode offers the next one, which starts at its end when the user plays episodes in a row.
* **Hiding**: the controls fade out after 3 seconds without input during playback.
* **Input**: keyboard shortcuts on desktops and the web (space, arrows, `f`, `m`, `j`/`l`); the D-pad and remote on television, where the controller follows the platform's focus (the tvOS focus engine, Compose for TV focus) and stays up while it has focus.

### 6.6 Copy and Localization
The strings of every client are defined once in `libs/design/strings` in ICU MessageFormat, with English the source language, and compiled into the web UI's message catalogs, String Catalogs (`.xcstrings`) for Apple platforms, `strings.xml` for Android and a Go package for the desktop app. The same term names the same thing everywhere, plurals follow CLDR rules, and each string is translated once. Strings only one platform uses carry that platform's tag.

### 6.7 Platform Conventions
Consistency of brand does not override the platforms:
* **Window chrome**: traffic lights on the left on macOS; caption buttons on the right on Windows and Linux.
* **Menus**: the macOS menu bar; context menus and popovers elsewhere; the menu of more actions is a menu on Apple platforms and desktops and a bottom sheet on Android phones.
* **Materials**: vibrancy on Apple platforms, Mica on Windows 11.
* **Touch**: targets of at least 44 × 44 pt, and safe areas respected.
* **Navigation**: the platform's back gesture and button; settings use the platform's controls (switches, pickers, lists).
* **Accessibility**: VoiceOver, TalkBack and screen readers, Dynamic Type and font scaling, Reduce Motion, and contrast meeting WCAG AA.

### 6.8 Galleries and Visual Review
* **Component galleries**: every platform browses its components in every state with fixed data — Storybook on the web, SwiftUI previews on Apple platforms, Compose previews on Android and a gallery window in the desktop app.
* **Snapshot tests**: every client renders the same set of screens with fixed data in snapshot tests — Playwright on the web, swift-snapshot-testing on Apple platforms, Roborazzi on Android and MyGo's tester (`ui.NewTester`), which draws frames in memory, in the desktop app. The Snapshots workflow, started by hand, compares them with the committed references and builds one page placing each screen's platforms side by side, which a pull request that changes the UI links for review.
  * `libs/design/snapshots/screens.json` names the screens, the sizes of the form factors (phone, tablet, desktop, TV) and the fixed data they are drawn with, a made-up library; each client maps the data into its own models, and a snapshot is named `<screen>-<size>.png`.
  * The web UI's tests (`apps/web/snapshots`) serve the built UI, the server's answers from the fixed data and generated artwork to the browser at `http://mavio.test`, with the clock fixed and Inter shipped with the UI, so that nothing comes from the network or the machine's fonts. The browser runs in Playwright's container image, the same on every machine, and the tests connect to it; the references are in `apps/web/snapshots/references`.
  * The Apple tests (`libs/apple/Tests/MavioUITests`) draw the screens with `MavioUI` on an iOS simulator in English, and are skipped on the Mac; the references are in `libs/apple/snapshots`.
  * The Android tests are unit tests of `libs/android/ui`, drawn by Robolectric's native graphics on the JVM, so that no emulator is needed; the references are in `libs/android/ui/snapshots`.
  * Each client's `snapshot` target compares and `snapshot-record` records the references. While the UI changes, the references are left as they are: they are recorded, compared and committed once before pushing, unless asked for sooner. `design:gallery` gathers the references into `dist/snapshots/gallery`, the page placing the platforms side by side.
* **Feature parity**: `libs/design/parity.md` lists every feature with its state on each client (shipped, planned, not applicable), so that a client lacks a feature only by decision; a pull request adding a feature to one client updates it.

## 7. Dependency Direction and Tooling

* `apps/web` → `libs/client-ts` → `libs/proto` (TypeScript); every client → `libs/design`.
* `apps/ios`, `apps/tvos`, `apps/macos` → `libs/apple` → `libs/client-rust` (Swift bindings).
* `apps/android`, `apps/android-tv` → `libs/android` → `libs/client-rust` (Kotlin bindings).
* `apps/desktop` → `libs/client-rust` (the C ABI, through its Go binding `libs/client-rust/capi`) and `libs/proto` (Go). It is a Go module like the server's and follows the repository's Go conventions; the depguard rules let it depend on no server library.
* `libs/client-rust` → `libs/proto` (Rust) and `libs/intent`; `libs/client-ts` loads `libs/intent`'s WASM build.
* No app depends on another app. The server depends on `apps/web` only for the files it embeds.
* Nx runs every client: `tools/nx-go` infers `apps/desktop` as it does every Go module, Vite and TypeScript run through their Nx plugins, and Cargo, Gradle and `xcodebuild` through targets of their own. The Apple and Android jobs in CI run only when they are affected, macOS runners being costly.
