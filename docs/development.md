## 1. Toolchain and Setup

Tool versions are pinned in `mise.toml`:

| Tool | Purpose |
| :--- | :--- |
| go | Server, libraries, plugins |
| node + pnpm | Nx, `protoc-gen-es`, and later the TS applications |
| buf | Protobuf lint, format, breaking-change checks and code generation |
| golangci-lint | Go linting and formatting checks |
| sqlc | Dialect-specific query code in `libs/store` |
| protoc-gen-buffa, protoc-gen-buffa-packaging, protoc-gen-connect-rust | Rust code generation of `libs/proto`, from their release builds |
| java (Temurin) + gradle | The Android apps and `libs/android` |
| jellyfin-ffmpeg | The media pipeline, test media generation and the integration tests (`ffmpeg` / `ffprobe` on `PATH`) |

```bash
mise install            # Install the pinned toolchain
pnpm install            # Install Nx
```

Rust is pinned by `libs/client-rust/rust-toolchain.toml`, which rustup installs on the first `cargo` command there; only rustup itself is needed.

Every target of the clients builds on that toolchain, the tvOS targets `aarch64-apple-tvos` and `aarch64-apple-tvos-sim` included, whose standard library rustup installs like the others' (`rustup target add aarch64-apple-tvos`).

Migrations are generated by `libs/store/internal/cmd/migrategen`, which uses Atlas as a library; no Atlas CLI is needed. Generating PostgreSQL migrations and running the PostgreSQL conformance tests needs Docker. `libs/store/pgtest` starts their containers on `DOCKER_HOST`, else on the engine of the Docker CLI's current context (`docker context use`), else on the first engine found at the sockets of Docker Desktop, OrbStack, Colima, Rancher Desktop or Podman; no further setup is needed.

## 2. Monorepo and Nx

### 2.1 Why Nx
Go is the main server language; later the [clients](clients.md) join it in TypeScript (the web UI), Swift, Kotlin, Go (the desktop app) and Rust (their shared core), using client code generated from `libs/proto`. This is a polyglot monorepo that needs a unified dependency graph, affected-project analysis and task caching:
* Nx has official plugins for Vite / React; Cargo, Gradle and `xcodebuild` run through targets of their own;
* Go projects are inferred by the in-repo local Nx plugin `tools/nx-go`: every `go.mod` automatically becomes a project, and the dependency graph is derived from in-repo `require` directives in `go.mod`;
* Cargo workspaces are inferred by the local Nx plugin `tools/nx-cargo`: every `Cargo.toml` with a `[workspace]` table becomes a project, depending on the projects its `[workspace.metadata.nx]` lists in `implicitDependencies` (`libs/client-rust` lists `proto`, whose generated Rust it includes);
* Boundaries are expressed with tags: `type:app|lib|plugin`, `lang:go|ts|rust|swift|kotlin`, `scope:server|client|shared`. The TS side is constrained by `@nx/enforce-module-boundaries`, the Go side by depguard (§5).

Nx only orchestrates and caches: every Go module still works on its own with `go build` / `go test`.

### 2.2 Inferred Targets
`tools/nx-go` gives every Go project these targets (project name = directory name):

| Target | Command | Cached |
| :--- | :--- | :--- |
| `build` | `go build ./...` with `CGO_ENABLED=0` | Yes |
| `test` | `go test ./...` | Yes |
| `bench` | `go test -run=NONE -bench=. -benchmem ./...` | No |
| `lint` | `golangci-lint run --allow-parallel-runners ./...` (Nx runs projects in parallel) | Yes |
| `tidy-check` | `go mod tidy -diff` with `GOWORK=off` | Yes |
| `generate` | `buf generate` (only projects with a `buf.yaml`) | No |
| `buf-lint` | `buf lint && buf format --diff --exit-code` (only projects with a `buf.yaml`) | Yes |

A project overrides a default target with a `project.json` next to its `go.mod`; for example `plugins/scraper-tmdb/project.json` builds a `wasip1` WASM module.

`tools/nx-cargo` gives every Cargo workspace `build` (`cargo build --locked --all-targets`), `test` (`cargo test --locked`), `bench` (`cargo bench --locked`, not cached) and `lint` (`cargo fmt --check` and `cargo clippy --locked --all-targets -- -D warnings`).

The scripts of a `package.json` are targets too: `libs/proto` and `libs/design` have `typecheck` (`tsc -p tsconfig.json`, TypeScript 7), and `libs/design` has `generate` (§4.4). A directory with both a `go.mod` and a `package.json`, such as `libs/design`, is one project with the targets of both.

`libs/client-rust/capi` is a crate of the Cargo workspace and a Go module, the C ABI's Go binding; as a Go project in the Cargo workspace's directory, it is the Nx project `capi`, whose files Nx counts as its own, so the Cargo targets of `client-rust` name its Rust sources among their inputs (`libs/client-rust/project.json`). Its `test` runs after `client-rust:build` with `CGO_ENABLED=0`, as the app builds, and loads the library from `target/debug`; `generate` runs `buf generate` for the C ABI's messages in `libs/client-rust/proto`, writing Go into `gen/` and Rust into `src/gen/` (both committed), and `buf-lint` checks them.

`libs/client-ts` and `apps/web` have `typecheck` as well, `libs/client-ts` has `test` (Vitest) and `apps/web` has `build` (Vite), which writes the web UI into `apps/server/internal/webui/dist`. The server's `build` and `dist` depend on it (`apps/server/project.json`), so that the binaries embed the UI; a plain `go build` embeds whatever the directory holds, and with only its `.gitkeep` the server serves a page saying it was built without the UI. `apps/web` has `snapshot` and `snapshot-record` too (`snapshots/run.sh`), which start Playwright's container image with Docker and run the snapshot tests against the browser in it, comparing with or recording the references. `libs/design` has `gallery`, which gathers every client's references into `dist/snapshots/gallery` ([Clients §6.8](clients.md#68-galleries-and-visual-review)). `pnpm --filter @mavio/web dev` serves the UI with Vite, sending its API calls to a server on port 8686.

The Apple projects need Xcode and build only on macOS; they carry the tag `platform:apple`, which the Linux and Windows CI jobs exclude. `libs/apple` has `core`, which runs `scripts/build-core.sh`: it builds `mavio-uniffi` for every Apple target, wraps each shared library in a dynamic framework, and writes `build/MavioCoreFFI.xcframework` with the Swift API UniFFI generates (`build/MavioCore`); a framework rather than a static library, because static libraries of other Rust code in an app (AetherEngine's LibDovi) carry their own Rust standard library, whose symbols would clash. Its `ass` target fetches libass from mavio-deps (below) into `build/Libass.xcframework`: libass with FreeType, FriBidi and HarfBuzz, a static library per platform, the one for macOS universal. Its `build` runs `swift build` after `core` and `ass`, and `test` runs `swift test` after `build`, whose `.build` it reuses, and `lint` runs `swift format lint --strict` with the repository's `.swift-format`; `snapshot` runs `scripts/snapshot.sh`, the snapshot tests on an iPhone simulator of the newest iOS, and `snapshot-record` records their references. `apps/ios`, `apps/tvos` and `apps/macos` have `build` (`xcodebuild` without signing, for the simulator on iPhone and Apple TV; arm64 only, as AetherEngine's simulator libraries are), `lint`, and `generate`, which writes the app's `Mavio.xcodeproj` with `libs/apple/scripts/gen-project.py`: the project is committed and never edited by hand, and its sources are the synchronized folder `Mavio/`, so adding a file needs no change to it.

The Android projects need the Android SDK, found through `ANDROID_HOME`, and run the Gradle and the JDK that `mise.toml` pins; each Gradle build's `gradle/wrapper/gradle-wrapper.properties` names the same Gradle for Android Studio, without a wrapper script. They carry the tag `platform:android`. `libs/android` (Nx name `android-lib`) is a Gradle build of the modules `core`, `player` and `ui`, with one version catalog (`gradle/libs.versions.toml`) that the apps' settings read too; its `core` target runs `scripts/build-core.sh`, which builds `mavio-uniffi` with the pinned NDK (installed with `sdkmanager` when missing) for `arm64-v8a`, `armeabi-v7a` and `x86_64`, and writes the libraries, the Kotlin API UniFFI generates and the core built for this machine, which the unit tests load through JNA, into `core/build/rust`. Its `mpv` target fetches libmpv from mavio-deps (below) into `player/build/mpv`: libmpv, FFmpeg, their libraries and mpv-android's JNI layer for the same ABIs, built with mpv-android's build scripts, and mpv-android's Kotlin API to the JNI layer. Its `ffmpeg` target fetches Media3's FFmpeg decoder extension from mavio-deps (below) into `player/build/ffmpeg`: `libffmpegJNI.so` for each ABI, the extension's JNI layer linked with FFmpeg's audio decoders as LGPL, and its audio renderer's Java sources; it is built for one Media3 version, and the build of `player` fails when the version catalog names another. Its `build`, `test` and `lint` run `assembleDebug`, `testDebugUnitTest` and `lintDebug`; `test` also compares the snapshots of `ui` with their references (`verifyRoborazziDebug`), and `snapshot-record` records them. `apps/android` and `apps/android-tv` are Gradle builds that include `libs/android` and depend on its modules by their coordinates (`dev.mavio.android:core`); they have `build` and `lint`. Gradle targets run one at a time, as the apps' builds share the included build.

Native libraries of the clients that take long to build come prebuilt from [mavio-deps](https://github.com/mavioai/mavio-deps), which builds them from source at pinned versions and releases each as a tag `<library>-<version>-<revision>` with the binaries, their sources, a manifest and checksums. `tools/deps/deps.txt` pins each library's tag and the SHA-256 of its binary asset, and `tools/deps/fetch.sh <library>`, which the targets above run, downloads the asset into `dist/deps`, fails when its digest differs and extracts it; a library already extracted at its pin is left as it is. CI keeps `dist/deps` in its cache, keyed by `deps.txt`, so that its runs download a pin once. Upgrading one is a new release of mavio-deps and a new pin here.

The `core` targets of `libs/apple` and `libs/android` build the core for all their targets in one Cargo build per toolchain, so that the targets compile in parallel, with the `release` profile; `MAVIO_CORE_PROFILE=dev` builds it without optimizations instead, which takes a fraction of the time, as CI does. The core and the app for macOS are universal, `arm64` and `x86_64`; `MAVIO_MACOS_ARCHS=arm64` builds them for Apple silicon only, as CI does. The core for the Apple platforms covers iOS, the iOS simulator, tvOS, the tvOS simulator and macOS; `MAVIO_APPLE_PLATFORMS` lists the ones to build, of `ios`, `ios-sim`, `tvos`, `tvos-sim` and `macos`, and each apple job of CI builds the one its builds and tests run on, `macos`, `ios-sim` or `tvos-sim`.

### 2.3 Common Commands
```bash
pnpm nx run-many -t build test lint tidy-check     # Check everything
pnpm nx affected -t build test lint tidy-check     # Check affected projects only
pnpm nx run proto:generate                         # Regenerate libs/proto/gen
pnpm nx run proto:buf-lint                         # buf lint + format check
pnpm nx run <project>:bench                        # Run a project's benchmarks
pnpm nx show projects                              # List projects
pnpm nx graph                                      # Show the project graph
```

`go test ./...` does not cross module boundaries; use `nx run-many` / `nx affected` to run across modules.

## 3. Go Modules

### 3.1 Conventions
* Every Go library, application and plugin has its own `go.mod`; the module path is `github.com/mavioai/mavio/<dir>`, e.g. `github.com/mavioai/mavio/libs/media`. The `go` directive is `1.27.0` everywhere.
* Dependencies between in-repo modules are declared both in `go.work` and in each `go.mod` as `require` + relative-path `replace`: `go.work` serves gopls and cross-module development, while `replace` keeps `go mod tidy` and builds working with `GOWORK=off` (`go mod tidy` does not read `go.work`). The `tidy-check` target validates every module's `go.mod` this way.
* Binary tools are pinned by mise; code generation plugins (`protoc-gen-go`, `protoc-gen-connect-go`, and later `sqlc`, `ent`) are pinned through the `tool` directive in the owning module's go.mod.
* If some modules turn out to always change together, merge them to avoid over-splitting.

### 3.2 Adding a Module
1. Create the directory and run `go mod init github.com/mavioai/mavio/<dir>`.
2. Change the `go` directive to `1.27.0`.
3. Add the directory to `use` in `go.work`.
4. Add a `doc.go` with the package comment.

Nx picks the new module up automatically; no `project.json` is needed.

### 3.3 Adding an In-repo Dependency
```bash
go mod edit -require=github.com/mavioai/mavio/libs/core@v0.0.0 -replace=github.com/mavioai/mavio/libs/core=../core
GOWORK=off go mod tidy
```
The new edge must respect the dependency direction in [Architecture §3.2](architecture.md#32-dependency-direction); depguard rejects violations (§5).

## 4. Code Generation

### 4.1 Protobuf and Connect
* Contract sources live in `libs/proto/mavio/<domain>/v1/` and use `edition = "2023"`; the package name is `mavio.<domain>.v1`.
* `buf generate` (configured in `libs/proto/buf.gen.yaml`) runs `protoc-gen-go` with `default_api_level=API_OPAQUE` (fields accessed through getters/setters) and `protoc-gen-connect-go` with `simple` (handlers take and return messages directly). Managed mode sets `go_package` under `github.com/mavioai/mavio/libs/proto/gen/go`.
* The same run generates `libs/proto/openapi/gen/mavio.openapi.json`, the OpenAPI document of the services the server serves, with `protoc-gen-connect-openapi` merging `openapi/base.yaml` (description, bearer authentication, the plain HTTP media routes). It runs through `go run` at a version pinned in `buf.gen.yaml`, so that its dependencies stay out of the go.mod third-party plugins import; package `openapi` embeds the document, which is committed like `gen/`.
* The same run generates TypeScript into `gen/ts` with `protoc-gen-es` (protobuf-es messages and the service descriptors connect-es uses; `libs/proto` is also the npm package `@mavio/proto`, exporting them), and Rust into `gen/rust` with `protoc-gen-buffa` (messages, in `gen/rust/proto`) and `protoc-gen-connect-rust` (clients, in `gen/rust/connect`), each tree given its `mod.rs` files by `protoc-gen-buffa-packaging`. The crate `mavio-api` of `libs/client-rust` includes the Rust trees.
* After changing a `.proto`, run `pnpm nx run proto:generate` and **commit the generated `gen/` code**. Never edit files under `gen/` by hand.
* `buf lint` uses the STANDARD rules and `buf breaking` the FILE rules. Published field numbers must never be reused; breaking changes go into a new `v2` package.
* Read-only RPCs are annotated with `option idempotency_level = NO_SIDE_EFFECTS;`.
* Request validation uses protovalidate annotations (`buf.validate`). Under edition 2023 every field tracks presence and rules apply only to fields that are set, so **mandatory fields must be marked `(buf.validate.field).required = true`**. `libs/proto/validate_test.go` checks the rules.

### 4.2 Database Schema and Queries
The pipeline is described in [Architecture §5.2](architecture.md#52-generation-pipeline). After changing the ent schema in `libs/store/internal/ent/schema`:

```bash
pnpm nx run store:generate                                   # ent client + sqlc code
# in libs/store
go run ./internal/cmd/migrategen -dialect sqlite -name <name>
go run ./internal/cmd/migrategen -dialect postgres -name <name>  # starts a PostgreSQL container; needs Docker
```

Review both migrations and commit them together with the schema change. Merged migration files must never be modified; only append new migrations. Dialect-specific queries live in `libs/store/queries/<dialect>/` and are generated by `sqlc` (pinned in `mise.toml`) as part of `store:generate`.

### 4.3 Plugins
Plugins register Connect handlers with `guest.Handle` and pick a runtime at build time (see [Architecture §7.4](architecture.md#74-plugin-sdk-structure)):

```bash
GOOS=wasip1 GOARCH=wasm go build -buildmode=c-shared -o plugin.wasm .   # WASM runtime
go build -o plugin .                                                     # process runtime
```

A plugin directory holds `manifest.json` and `plugin.wasm` or `plugin` (`plugin.exe` on Windows).

### 4.4 Design System
`pnpm nx run design:generate` runs `libs/design/build/build.js`, which compiles the sources of the design system ([Clients §6](clients.md#6-design-system)) into `libs/design/gen`:

| Source | Contents |
| :--- | :--- |
| `tokens/*.json` | Design tokens in the DTCG format, resolved by Style Dictionary; one file per theme (`color.dark`, `color.light`), type scale (`typography.default`, `typography.tv`) and form factor (`layout.*`) |
| `icons/icons.json` | Semantic icon names mapped to Phosphor names; the SVGs, Regular and Fill, come from `@phosphor-icons/core` at its pinned version and are copied into `icons/svg` |
| `strings/<locale>.json` | Strings in ICU MessageFormat with a description, and the platforms a string is limited to; English (`en.json`) is the source |

| Output | For |
| :--- | :--- |
| `gen/ts` | The web UI: `tokens.ts`, `tokens.css` (custom properties, the light theme under `prefers-color-scheme`), `icons.ts` (path data), `strings.ts`; the npm package `@mavio/design` exports them |
| `gen/swift` | Apple platforms: `MavioTokens.swift` (SwiftUI), `Icons.xcassets`, `Localizable.xcstrings` |
| `gen/kotlin` | Android: `dev/mavio/design/MavioTokens.kt` (Compose), `res/drawable` (vector drawables), `res/values*/strings.xml` |
| `gen/go` | The desktop app: the Go package `design` (module `github.com/mavioai/mavio/libs/design`) with the tokens, icon path data, the strings and their formatter |

* The generator fails on a text and background pair below WCAG AA contrast (4.5:1) in either theme, on a message whose plural lacks a CLDR category of its locale, and on a translation whose arguments differ from the source's.
* Messages are limited to the ICU subset every platform's format expresses: text, `{arg}`, and one plural over the whole message whose forms hold the count (`#`) and text.
* Commit `gen/` with its sources; never edit it by hand.

## 5. Code Quality

`.golangci.yml` (golangci-lint v2) applies to every Go module:
* **Linters**: the `standard` set plus `depguard`, `errorlint`, `misspell`, `nolintlint`, `unconvert`, `usestdlibvars`; generated code is excluded.
* **Formatters**: `gofumpt` and `goimports`, with `github.com/mavioai/mavio` imports in their own group.
* **depguard**: encodes the dependency direction from [Architecture §3.2](architecture.md#32-dependency-direction) as rules (`core` only on the standard library, pure libraries only on `core`, the plugin SDK only on `libs/proto`, no lib importing `apps/*` or `plugins/*`, …). To change the dependency direction, update the architecture document first, then the rules.

## 6. Continuous Integration

`.github/workflows/ci.yml` runs on pushes to `main` and on pull requests. Every job starts once **plan** has found what the change affects, and a job whose projects it does not affect is skipped; a change to `.github` or `mise.toml` affects every project:
* **plan** (Linux): lists the affected Apple and Android projects, and whether the web UI, and the server or a library it is built from, are affected.
* **check** (Linux): `nx affected -t buf-lint lint tidy-check typecheck build test`; regenerates code and fails on any diff; runs `buf breaking` against the base branch on pull requests.
* **test**: `nx run-many -t typecheck test build` on linux arm64, macOS and Windows; pull requests run `nx affected` instead.
* **apple** (macOS with Xcode 27, the runners' `xcode-27` image, as the `Package.resolved` files and the references of the snapshots are made with Xcode 27), a job per platform, and one for the snapshot tests, so that their builds do not share a runner's cores: **Apple (macOS)** for `libs/apple` and `apps/macos`, **Apple (iOS)** for `apps/ios`, **Apple (tvOS)** for `apps/tvos`, each when **plan** finds any of its projects affected. Each runs `nx run-many -t lint build test` over its affected projects, with the core built by the `dev` profile for its platform only, and fails when their generated Xcode projects differ from what `generate` writes; when `libs/apple` is affected, **Apple (iOS snapshots)** runs its snapshot tests on the simulator, with the core for the iOS simulator, uploading the snapshots that differ.
* **android** (Linux), when **plan** finds Android projects affected: `nx run-many -t lint build test` over them, with the core built by the `dev` profile; uploads the images of snapshots that differ.
* **web-snapshots** (linux arm64, as the references are recorded on Apple silicon), when the web UI is affected: `nx run web:snapshot`, then `design:gallery`, uploading the gallery and the results of the comparison.
* **media** (Linux, macOS), when the server is affected: installs jellyfin-ffmpeg, generates the fixtures and runs the `media`, `streaming` and `server` tests without the Nx cache, so the ffmpeg integration and smoke tests run on the runners' hardware.
* **dist** (Linux), when the server is affected: `nx run server:dist`, so the server cross-compiles for every supported platform; the platforms build in parallel.
* **image** (Linux), when the server is affected: builds the container image for linux/amd64 and linux/arm64 without pushing it, then runs the amd64 image until its health check passes.

Toolchains in CI come from the same `mise.toml` (`jdx/mise-action`); jobs other than **media** leave jellyfin-ffmpeg out, and jobs other than **android** Java and Gradle (`MISE_DISABLE_TOOLS`). Rust comes from `rust-toolchain.toml` through the runners' rustup, and **check**, **test**, **apple** and **android** cache Cargo's builds (`Swatinem/rust-cache`), **apple** and **android** under a key of their core's profile, **apple** of its platform too. **apple** caches the clones of the Swift packages that SwiftPM and `xcodebuild` share (`~/Library/Caches/org.swift.swiftpm`), under a key of the `Package.resolved` files, and **android** Gradle's home, with its dependencies and build cache (`gradle/actions/setup-gradle`). **check**, **test**, **media** and **dist** cache Go's builds and modules, and **check** golangci-lint's results (`.github/actions/go-cache`): the caches are saved only on pushes to `main`, and pull requests restore the latest of them. **media** runs Go's tests with `-count=1`, so that their cached results do not replay. Caches are saved only on pushes to `main`; after the jobs of such a push, **caches** deletes the caches of `main` that newer ones replaced, those saved for earlier commits or toolchains, and `.github/workflows/pr-caches.yml` deletes a pull request's caches once it closes.

## 7. Releases and Versioning

`libs/proto` and `libs/plugin` are imported by third-party plugins and are published independently with path-prefixed tags (e.g. `libs/proto/v0.1.0`, `libs/plugin/v0.1.0`). Their `replace` directives have no effect on consumers, so:
1. Release `libs/proto` first.
2. Update the `require` of `libs/plugin` to that version, then release `libs/plugin`.

Other modules are used only inside the repository and promise no stable external API.

The server's release binaries are built with `VERSION=v0.1.0 pnpm nx run server:dist`, and its image with `docker buildx build -f apps/server/Dockerfile --build-arg VERSION=v0.1.0 --platform linux/amd64,linux/arm64 .` from the repository root. The Dockerfile pins the same jellyfin-ffmpeg version as `mise.toml`, with the SHA-256 digests of its two Linux portable builds; upgrading jellyfin-ffmpeg changes both files, and a test (`apps/server/internal/buildinfo`) fails when the two pins disagree. The image also builds the DLNA, indexers and download clients plugins and ships them in `/usr/lib/mavio/plugins`, the plugin seed folder.

First-party process plugins are packaged with their `dist` target: `pnpm nx run dlna:dist` (or `indexers:dist`, `download-clients:dist`) builds the DLNA (or indexers, download clients) plugin, at the version in its manifest, for every server platform into `plugins/<name>/dist/`, as one catalog zip per platform and a `catalog.json` listing them with their SHA-256 digests; the zips' URLs are relative to the catalog.

Release builds of `scraper-tmdb` set `MAVIO_TMDB_KEY` to Mavio's own TMDB API key, which `pnpm nx run scraper-tmdb:build` builds into the plugin as the key used once TMDB rejects Radarr's token ([Architecture §13.2](architecture.md#132-data-sources-and-numbering)); the key is never committed.

## 8. Commits and Documentation

* Use Conventional Commits with the Nx project name as scope: `feat(naming): parse absolute episode numbers`, `build(nx): …`, `docs: …`. Keep each commit to a single purpose, and make sure `pnpm nx affected -t build test lint tidy-check` passes before committing.
* Every document exists in English (`<name>.md`) and Simplified Chinese (`<name>.zh-CN.md`) with section-by-section correspondence; the two link to each other at the top, and both are updated in the same commit.
* Documents describe only the approaches that were adopted.
