## 1. Toolchain and Setup

Tool versions are pinned in `mise.toml`:

| Tool | Purpose |
| :--- | :--- |
| go | Server, libraries, plugins |
| node + pnpm | Nx, `protoc-gen-es`, and later the TS applications |
| buf | Protobuf lint, format, breaking-change checks and code generation |
| protoc | Its built-in Python generators, which `buf generate` runs for `libs/proto/gen/python` |
| golangci-lint | Go linting and formatting checks |
| sqlc | Dialect-specific query code in `libs/store` |
| protoc-gen-buffa, protoc-gen-buffa-packaging, protoc-gen-connect-rust | Rust code generation of `libs/proto`, from their release builds |
| python + uv | Python process plugins (`plugins/pipecat`) and the Python SDK (`libs/plugin/python`), in the uv workspace of the root `pyproject.toml`; uv also fetches the python-build-standalone builds packaged with them |
| java (Temurin) + gradle | The Android apps and `libs/android` |
| jellyfin-ffmpeg | The media pipeline, test media generation and the integration tests (`ffmpeg` / `ffprobe` on `PATH`) |
| rclone (mavioai/rclone) | Libraries on rclone remotes and their integration tests (`rclone` on `PATH`), from the fork's release builds |

```bash
mise install            # Install the pinned toolchain
pnpm install            # Install Nx
```

`pnpm nx` runs Nx under `mise exec` (the `nx` script of `package.json`), so every target runs the pinned tools whether or not the shell activates mise; a tool on `PATH` with the same name, such as an upstream rclone, is not used. Commands run outside Nx, such as `go test` in a module, run under `mise exec --` too, or in a shell that activates mise.

Rust is pinned by `libs/client-rust/rust-toolchain.toml`, which rustup installs on the first `cargo` command there; only rustup itself is needed.

Every target of the clients builds on that toolchain, the tvOS targets `aarch64-apple-tvos` and `aarch64-apple-tvos-sim` included, whose standard library rustup installs like the others' (`rustup target add aarch64-apple-tvos`).

Migrations are generated by `libs/store/internal/cmd/migrategen`, which uses Atlas as a library; no Atlas CLI is needed. Generating PostgreSQL migrations and running the PostgreSQL conformance tests needs Docker. `libs/store/pgtest` starts their containers on `DOCKER_HOST`, else on the engine of the Docker CLI's current context (`docker context use`), else on the first engine found at the sockets of Docker Desktop, OrbStack, Colima, Rancher Desktop or Podman; no further setup is needed.

npm packages that need a fix their release does not have yet are patched with `pnpm patch` / `pnpm patch-commit`: the patch is in `patches/`, listed under `patchedDependencies` in `pnpm-workspace.yaml`, and `pnpm install` applies it. Each patch carries only a fix the package's upstream has already made, and goes as soon as a release has it: upgrade the package, then remove the patch and its entry (`pnpm patch-remove`).

| Patch | Fix | Goes with |
| :--- | :--- | :--- |
| `hls.js@1.7.3.patch` | The subtitles stop after hls.js attaches to the video again (`recoverMediaError`, as when the video moves into the Picture in Picture window or the network changes): `SubtitleStreamController.onSubtitleFragProcessed` takes the track's buffered ranges as they come (`tracksBuffered[frag.level] ||= []`), as on hls.js's `master` | The first hls.js release after 1.7.3 with that line |

## 2. Monorepo and Nx

### 2.1 Why Nx
Go is the main server language; later the [clients](clients.md) join it in TypeScript (the web UI), Swift, Kotlin, Go (the desktop app) and Rust (their shared core), using client code generated from `libs/proto`. This is a polyglot monorepo that needs a unified dependency graph, affected-project analysis and task caching:
* Nx has official plugins for Vite / React; Cargo, Gradle and `xcodebuild` run through targets of their own;
* Go projects are inferred by the in-repo local Nx plugin `tools/nx-go`: every `go.mod` automatically becomes a project, and the dependency graph is derived from in-repo `require` directives in `go.mod`;
* Cargo workspaces are inferred by the local Nx plugin `tools/nx-cargo`: every `Cargo.toml` with a `[workspace]` table becomes a project, depending on the projects its `[workspace.metadata.nx]` lists in `implicitDependencies` (`libs/client-rust` lists `proto`, whose generated Rust it includes);
* Python projects are inferred by the local Nx plugin `tools/nx-uv`: every member of the uv workspace becomes a project, depending on the workspace members its `pyproject.toml` requires and on `proto` for the generated Python it imports;
* Boundaries are expressed with tags: `type:app|lib|plugin`, `lang:go|ts|rust|python|swift|kotlin`, `scope:server|client|shared`. The TS side is constrained by `@nx/enforce-module-boundaries`, the Go side by depguard (§5).

Nx only orchestrates and caches: every Go module still works on its own with `go build` / `go test`.

### 2.2 Inferred Targets
`tools/nx-go` gives every Go project these targets (project name = directory name):

| Target | Command | Cached |
| :--- | :--- | :--- |
| `build` | `go build ./...` with `CGO_ENABLED=0` | Yes |
| `test` | `go test ./...` | Yes |
| `bench` | `go test -run=NONE -bench=. -benchmem ./...` | No |
| `lint` | `golangci-lint run --allow-parallel-runners ./...` (Nx runs projects in parallel) | Yes |
| `tidy-check` | `go mod tidy -diff` with `GOWORK=off` | Yes |
| `generate` | `buf generate` (only projects with a `buf.yaml`) | No |
| `buf-lint` | `buf lint && buf format --diff --exit-code` (only projects with a `buf.yaml`) | Yes |

A project overrides a default target with a `project.json` next to its `go.mod`; for example `plugins/scraper-tmdb/project.json` builds a `wasip1` WASM module.

`tools/nx-cargo` gives every Cargo workspace `build` (`cargo build --locked --all-targets`), `test` (`cargo test --locked`), `bench` (`cargo bench --locked`, not cached) and `lint` (`cargo fmt --check` and `cargo clippy --locked --all-targets -- -D warnings`). `libs/intent` adds `wasm`, which builds the grammar for `wasm32-unknown-unknown` and copies the module into `libs/intent/dist` (the npm package `@mavio/intent`, which `libs/client-ts`'s tests load) and `apps/server/internal/assistant/intent/dist` (which the server embeds); neither copy is committed, so the server's `build` and `libs/client-ts`'s `test` depend on it.

The scripts of a `package.json` are targets too: `libs/proto` and `libs/design` have `typecheck` (`tsc -p tsconfig.json`, TypeScript 7), and `libs/design` has `generate` (§4.4). A directory with both a `go.mod` and a `package.json`, such as `libs/design`, is one project with the targets of both. `libs/plugin` is one too: its TypeScript SDK `@mavio/plugin` has `typecheck` and `test-ts` (Vitest), on which its Go `test` depends, since a script named `test` would replace the inferred one.

`plugins/agent` is a TypeScript process plugin run by Bun, the version `mise.toml` pins: it has `typecheck`, `test` (`bun test`), `build` (`bun build --compile`: one executable for this platform, beside its manifest in `dist/plugin`, a plugin folder the server can start; `bun scripts/build.ts linux/arm64 <folder>` builds another platform's, into another folder). The executable carries Bun's runtime, so the server needs nothing installed for it; Bun runs `node:http2`, `node:sqlite` and the npm packages unchanged. Its dependencies come from the pnpm workspace, as the web UI's do; packages whose install scripts nothing needs are refused in `allowBuilds` of `pnpm-workspace.yaml`.

`tools/nx-uv` gives every member of the uv workspace `test` (`uv run --frozen pytest`), `lint` (`ruff check`, `ruff format --check` and `pyright`) and `tidy-check` (`uv lock --check`); `plugins/pipecat` adds `build`, which assembles a plugin folder for this platform in `dist/plugin` — its manifest, locales, a python-build-standalone CPython, its dependencies installed by `uv pip install --target` from the lock and its launcher — built by `tools/plugindist` (`go run ./cmd/plugindist -python ../../plugins/pipecat [-platform linux/arm64] [-folder <folder>]`), which builds for another platform as well, since uv installs any platform's wheels (`--python-platform`, `--only-binary` for every package but the pure-Python ones without wheels the project lists in `[tool.mavio] sdists`); it packages for the platforms whose wheels every dependency has, Linux on amd64 and arm64 and macOS on arm64, and skips the others ([Architecture §12](architecture.md#12-distribution)).

`libs/client-rust/capi` is a crate of the Cargo workspace and a Go module, the C ABI's Go binding; as a Go project in the Cargo workspace's directory, it is the Nx project `capi`, whose files Nx counts as its own, so the Cargo targets of `client-rust` name its Rust sources among their inputs (`libs/client-rust/project.json`). Its `test` runs after `client-rust:build` with `CGO_ENABLED=0`, as the app builds, and loads the library from `target/debug`; `generate` runs `buf generate` for the C ABI's messages in `libs/client-rust/proto`, writing Go into `gen/` and Rust into `src/gen/` (both committed), and `buf-lint` checks them.

`libs/client-ts` and `apps/web` have `typecheck` as well, `libs/client-ts` has `test` (Vitest) and `apps/web` has `build` (Vite), which writes the web UI into `apps/server/internal/webui/dist`. The server's `build` and `dist` depend on it (`apps/server/project.json`), so that the binaries embed the UI; a plain `go build` embeds whatever the directory holds, and with only its `.gitkeep` the server serves a page saying it was built without the UI. `apps/web` has `snapshot` and `snapshot-record` too (`snapshots/run.sh`), which start Playwright's container image with Docker and run the snapshot tests against the browser in it, comparing with or recording the references. `libs/design` has `gallery`, which gathers every client's references into `dist/snapshots/gallery` ([Clients §6.8](clients.md#68-galleries-and-visual-review)). During development the UI runs apart from the server: `pnpm --filter @mavio/web dev` serves it with Vite, which reloads changes in place, and sends its API calls to the server at `MAVIO_SERVER`, by default one on port 8686, such as `MAVIO_SERVER=http://127.0.0.1:8688 pnpm --filter @mavio/web dev`. `VITE_MAVIO_DEV_URL`, the base URL of mavio.dev's API, makes it the app of mavio.dev (app.mavio.dev), signing in only Mavio accounts. To reach it from other devices on the network, whose browsers sign in only in secure contexts, `DEV_TLS_CERT` and `DEV_TLS_KEY`, a certificate and key in PEM for the machine's address that those devices trust, such as ones made by mkcert, serve it over HTTPS on every interface; it then signs in through its server, whose `--mavio-dev-url` is mavio.dev served on the network the same way ([mavio.dev §2](mavio-dev.md)). Run apart from a desktop session, the server takes `--open-browser=false`, so that a new server does not open its setup in the browser.

The shared core of the native apps trusts the Mozilla roots alone. `MAVIO_EXTRA_CA_CERTS`, a PEM file of further certificate authorities, as Node.js's `NODE_EXTRA_CA_CERTS`, makes it trust a mavio.dev served on the network with a certificate of mkcert's (`$(mkcert -CAROOT)/rootCA.pem`); the iOS simulator passes it to the app as `SIMCTL_CHILD_MAVIO_EXTRA_CA_CERTS` on `xcrun simctl launch`, and a debug build of the iPhone and iPad app on a device, or of the Android app, takes it from `dev-ca.pem` in its files, put there with `xcrun devicectl device copy to --domain-type appDataContainer --domain-identifier dev.mavio.app --destination Documents/dev-ca.pem` or `adb push`.

`apps/website` (Nx name `website`, mavio.dev) has `typecheck`, `build` (`cf build`, Cloudflare's command line, running Vite with Cloudflare's plugin, which builds the Worker into `.cloudflare/output`) and `test` (Vitest, against PGlite, an in-process PostgreSQL, with the Connect services and better-auth behind the Worker's own request handler); `generate-auth-schema` and `generate-migration` regenerate its schema and migrations ([mavio.dev §2](mavio-dev.md#2-website-and-api-appswebsite)).

The Apple projects need Xcode and build only on macOS; they carry the tag `platform:apple`, which the Linux and Windows CI jobs exclude. `libs/apple` has `core`, which runs `scripts/build-core.sh`: it builds `mavio-uniffi` for every Apple target with the feature `dovi` (libdovi, whose C API the AetherEngine fork calls), wraps each shared library in a dynamic framework, and writes `build/MavioCoreFFI.xcframework` with the Swift API UniFFI generates (`build/MavioCore`); a framework rather than a static library, because a static library of other Rust code in an app would carry its own Rust standard library, whose symbols would clash. Its `ass` target fetches libass from mavio-deps (below) into `build/Libass.xcframework`: libass with FreeType, FriBidi and HarfBuzz, a static library per platform, the one for macOS universal. Its `generate` runs `scripts/gen-proto.sh`, which builds protoc-gen-swift from the swift-protobuf the package depends on, so that the messages match its runtime, and generates the Swift messages of `libs/proto` into `gen/MavioProto`, committed and never edited by hand, which the Apple job of CI checks are up to date. Its `build` runs `swift build` after `core` and `ass`, and `test` runs `swift test` after `build`, whose `.build` it reuses, and `lint` runs `swift format lint --strict` with the repository's `.swift-format`; `snapshot` runs `scripts/snapshot.sh`, the snapshot tests on an iPhone simulator of the newest iOS, and `snapshot-record` records their references. `apps/ios`, `apps/tvos` and `apps/macos` have `build` (`xcodebuild` without signing, for the simulator on iPhone and Apple TV, the iPhone app signed ad hoc so that the simulator's Keychain keeps its secrets; arm64 only, as AetherEngine's simulator libraries are), `lint`, and `generate`, which writes the app's `Mavio.xcodeproj` with `libs/apple/scripts/gen-project.py`: the project is committed and never edited by hand, and its sources are the synchronized folder `Mavio/`, so adding a file needs no change to it.

The Android projects need the Android SDK, found through `ANDROID_HOME`, and run the Gradle and the JDK that `mise.toml` pins; each Gradle build's `gradle/wrapper/gradle-wrapper.properties` names the same Gradle for Android Studio, without a wrapper script. They carry the tag `platform:android`. `libs/android` (Nx name `android-lib`) is a Gradle build of the modules `core`, `player`, `ui` and `admin`, with one version catalog (`gradle/libs.versions.toml`) that the apps' settings read too; its `core` target runs `scripts/build-core.sh`, which builds `mavio-uniffi` with the pinned NDK (installed with `sdkmanager` when missing) for `arm64-v8a`, `armeabi-v7a` and `x86_64`, and writes the libraries, the Kotlin API UniFFI generates and the core built for this machine, which the unit tests load through JNA, into `core/build/rust`. Its `mpv` target fetches libmpv from mavio-deps (below) into `player/build/mpv`: libmpv, FFmpeg, their libraries and mpv-android's JNI layer for the same ABIs, built with mpv-android's build scripts, and mpv-android's Kotlin API to the JNI layer. Its `ffmpeg` target fetches Media3's FFmpeg decoder extension from mavio-deps (below) into `player/build/ffmpeg`: `libffmpegJNI.so` for each ABI, the extension's JNI layer linked with FFmpeg's audio decoders as LGPL, and its audio renderer's Java sources; it is built for one Media3 version, and the build of `player` fails when the version catalog names another. Its `build`, `test` and `lint` run `assembleDebug`, `testDebugUnitTest` and `lintDebug`; `snapshot` compares the snapshots of `ui` with their references (`verifyRoborazziDebug`), and `snapshot-record` records them. `apps/android` and `apps/android-tv` are Gradle builds that include `libs/android` and depend on its modules by their coordinates (`dev.mavio.android:core`); they have `build` and `lint`, and `release` (`assembleRelease`), which CI runs too: a release build shrunk by R8, with the keep rules of `core` (JNA and the core's UniFFI API, the protobuf-lite messages) and `player` (the JNI classes of libmpv and the FFmpeg extension) in their `consumer-rules.pro`, signed with the key the Gradle properties `mavio.signing.storeFile`, `.storePassword`, `.keyAlias` and `.keyPassword` name, else with the debug key, so that it installs over a debug build on a device and keeps its data. Each app's `baselineprofile` module generates its baseline profile, of its start and Home, into `src/release/generated/baselineProfiles`, committed, which profileinstaller installs: `gradle :generateReleaseBaselineProfile` with `ANDROID_SERIAL` naming a connected device of API 33 or later, or a rooted one, on which the app is signed in to a server; `gradle :baselineprofile:connectedBenchmarkReleaseAndroidTest` measures the cold start uncompiled and with the profile. The phone's is generated on a phone, the television's on an Android TV emulator. Gradle targets run one at a time, as the apps' builds share the included build.

Native libraries of the clients that take long to build come prebuilt from [mavio-deps](https://github.com/mavioai/mavio-deps), which builds them from source at pinned versions and releases each as a tag `<library>-<version>-<revision>` with the binaries, their sources, a manifest and checksums. `tools/deps/deps.txt` pins each library's tag and the SHA-256 of its binary asset, and `tools/deps/fetch.sh <library>`, which the targets above run, downloads the asset into `dist/deps`, fails when its digest differs and extracts it; a library already extracted at its pin is left as it is. CI keeps `dist/deps` in its cache, keyed by `deps.txt`, so that its runs download a pin once. Upgrading one is a new release of mavio-deps and a new pin here.

The `core` targets of `libs/apple` and `libs/android` build the core for all their targets in one Cargo build per toolchain, so that the targets compile in parallel, with the `release` profile; `MAVIO_CORE_PROFILE=dev` builds it without optimizations instead, which takes a fraction of the time, as CI does. The core and the app for macOS are universal, `arm64` and `x86_64`; `MAVIO_MACOS_ARCHS=arm64` builds them for Apple silicon only, as CI does. The core for the Apple platforms covers iOS, the iOS simulator, tvOS, the tvOS simulator and macOS; `MAVIO_APPLE_PLATFORMS` lists the ones to build, of `ios`, `ios-sim`, `tvos`, `tvos-sim` and `macos`, and each apple job of CI builds the one its builds and tests run on, `macos`, `ios-sim` or `tvos-sim`.

### 2.3 Common Commands
```bash
pnpm nx run-many -t build test lint tidy-check     # Check everything
pnpm nx affected -t build test lint tidy-check     # Check affected projects only
pnpm nx run proto:generate                         # Regenerate libs/proto/gen
pnpm nx run proto:buf-lint                         # buf lint + format check
pnpm nx run <project>:bench                        # Run a project's benchmarks
pnpm nx show projects                              # List projects
pnpm nx graph                                      # Show the project graph
```

`go test ./...` does not cross module boundaries; use `nx run-many` / `nx affected` to run across modules.

## 3. Go Modules

### 3.1 Conventions
* Every Go library, application and plugin has its own `go.mod`; the module path is `github.com/mavioai/mavio/<dir>`, e.g. `github.com/mavioai/mavio/libs/media`. The `go` directive is `1.27.1` everywhere.
* Dependencies between in-repo modules are declared both in `go.work` and in each `go.mod` as `require` + relative-path `replace`: `go.work` serves gopls and cross-module development, while `replace` keeps `go mod tidy` and builds working with `GOWORK=off` (`go mod tidy` does not read `go.work`). The `tidy-check` target validates every module's `go.mod` this way.
* Binary tools are pinned by mise; code generation plugins (`protoc-gen-go`, `protoc-gen-connect-go`, and later `sqlc`, `ent`) are pinned through the `tool` directive in the owning module's go.mod.
* If some modules turn out to always change together, merge them to avoid over-splitting.

### 3.2 Adding a Module
1. Create the directory and run `go mod init github.com/mavioai/mavio/<dir>`.
2. Change the `go` directive to `1.27.1`.
3. Add the directory to `use` in `go.work`.
4. Add a `doc.go` with the package comment.

Nx picks the new module up automatically; no `project.json` is needed.

### 3.3 Adding an In-repo Dependency
```bash
go mod edit -require=github.com/mavioai/mavio/libs/core@v0.0.0 -replace=github.com/mavioai/mavio/libs/core=../core
GOWORK=off go mod tidy
```
The new edge must respect the dependency direction in [Architecture §3.2](architecture.md#32-dependency-direction); depguard rejects violations (§5).

## 4. Code Generation

### 4.1 Protobuf and Connect
* Contract sources live in `libs/proto/mavio/<domain>/v1/` and use `edition = "2023"`; the package name is `mavio.<domain>.v1`.
* `buf generate` (configured in `libs/proto/buf.gen.yaml`) runs `protoc-gen-go` with `default_api_level=API_OPAQUE` (fields accessed through getters/setters) and `protoc-gen-connect-go` with `simple` (handlers take and return messages directly). Managed mode sets `go_package` under `github.com/mavioai/mavio/libs/proto/gen/go`.
* The same run generates `libs/proto/openapi/gen/mavio.openapi.json`, the OpenAPI document of the services the server serves, with `protoc-gen-connect-openapi` merging `openapi/base.yaml` (description, bearer authentication, the plain HTTP media routes). It runs through `go run` at a version pinned in `buf.gen.yaml`, so that its dependencies stay out of the go.mod third-party plugins import; package `openapi` embeds the document, which is committed like `gen/`.
* The same run generates TypeScript into `gen/ts` with `protoc-gen-es` (protobuf-es messages and the service descriptors connect-es uses; `libs/proto` is also the npm package `@mavio/proto`, exporting them), and Rust into `gen/rust` with `protoc-gen-buffa` (messages, in `gen/rust/proto`) and `protoc-gen-connect-rust` (clients, in `gen/rust/connect`), each tree given its `mod.rs` files by `protoc-gen-buffa-packaging`. The crate `mavio-api` of `libs/client-rust` includes the Rust trees.
* The same run generates Python into `gen/python` with protoc's built-in `python` and `pyi` generators (protoc pinned by mise to the version of the protobuf runtime `mavio-proto` requires) and `protoc-gen-connect-python` (run by `uv run` from the development group of `mavio-proto`, at the version of its connect-python), the package `mavio-proto` of the uv workspace, which the Python SDK and plugins import.
* After changing a `.proto`, run `pnpm nx run proto:generate` and **commit the generated `gen/` code**. Never edit files under `gen/` by hand.
* `buf lint` uses the STANDARD rules and `buf breaking` the FILE rules. Published field numbers must never be reused; breaking changes go into a new `v2` package.
* Read-only RPCs are annotated with `option idempotency_level = NO_SIDE_EFFECTS;`.
* Request validation uses protovalidate annotations (`buf.validate`). Under edition 2023 every field tracks presence and rules apply only to fields that are set, so **mandatory fields must be marked `(buf.validate.field).required = true`**. `libs/proto/validate_test.go` checks the rules.

### 4.2 Database Schema and Queries
The pipeline is described in [Architecture §5.2](architecture.md#52-generation-pipeline). After changing the ent schema in `libs/store/internal/ent/schema`:

```bash
pnpm nx run store:generate                                   # ent client + sqlc code
# in libs/store
go run ./internal/cmd/migrategen -dialect sqlite -name <name>
go run ./internal/cmd/migrategen -dialect postgres -name <name>  # starts a PostgreSQL container; needs Docker
```

Review both migrations and commit them together with the schema change. Merged migration files must never be modified; only append new migrations. Dialect-specific queries live in `libs/store/queries/<dialect>/` and are generated by `sqlc` (pinned in `mise.toml`) as part of `store:generate`.

### 4.3 Plugins
Plugins register Connect handlers with `guest.Handle` and pick a runtime at build time (see [Architecture §7.4](architecture.md#74-plugin-sdk-structure)):

```bash
GOOS=wasip1 GOARCH=wasm go build -buildmode=c-shared -o plugin.wasm .   # WASM runtime
go build -o plugin .                                                     # process runtime
```

Python process plugins use the Python SDK (`mavio-plugin`) and are built by their `build` target (§2.2).

A plugin directory holds `manifest.json`, `plugin.wasm` or `plugin` (`plugin.exe` on Windows; for a Python plugin, its launcher beside its `python/`, which holds its dependencies in `site-packages`), and optionally `locales/<BCP 47 tag>.json`, the translations of the manifest's strings keyed by the English ([Architecture §7.5](architecture.md#75-plugins-in-the-server)).

### 4.4 Design System
`pnpm nx run design:generate` runs `libs/design/build/build.js`, which compiles the sources of the design system ([Clients §6](clients.md#6-design-system)) into `libs/design/gen`:

| Source | Contents |
| :--- | :--- |
| `tokens/*.json` | Design tokens in the DTCG format, resolved by Style Dictionary; one file per theme (`color.dark`, `color.light`), type scale (`typography.default`, `typography.tv`) and form factor (`layout.*`) |
| `icons/icons.json` | Semantic icon names mapped to Phosphor names; the SVGs, Regular and Fill, come from `@phosphor-icons/core` at its pinned version and are copied into `icons/svg` |
| `strings/<locale>.json` | Strings in ICU MessageFormat with a description, and the platforms a string is limited to; English (`en.json`) is the source |

| Output | For |
| :--- | :--- |
| `gen/ts` | The web UI: `tokens.ts`, `tokens.css` (custom properties, the light theme under `prefers-color-scheme`), `icons.ts` (path data), `strings.ts`; the npm package `@mavio/design` exports them |
| `gen/swift` | Apple platforms: `MavioTokens.swift` (SwiftUI), `Icons.xcassets`, `Localizable.xcstrings` |
| `gen/kotlin` | Android: `dev/mavio/design/MavioTokens.kt` (Compose), `res/drawable` (vector drawables), `res/values*/strings.xml` |
| `gen/go` | The desktop app: the Go package `design` (module `github.com/mavioai/mavio/libs/design`) with the tokens, icon path data, the strings and their formatter |

* The generator fails on a text and background pair below WCAG AA contrast (4.5:1) in either theme, on a message whose plural lacks a CLDR category of its locale, and on a translation whose arguments differ from the source's.
* Messages are limited to the ICU subset every platform's format expresses: text, `{arg}`, and one plural over the whole message whose forms hold the count (`#`) and text.
* Commit `gen/` with its sources; never edit it by hand.

## 5. Code Quality

Python follows the root `pyproject.toml`'s ruff and pyright settings: Python 3.14, the newest whose wheels every dependency has on every platform, ruff's formatter and its `E`, `F`, `I`, `B`, `UP`, `ASYNC` and `RUF` rules, pyright in strict mode, asyncio throughout with no blocking call on the event loop, and the messages and stubs of `libs/proto/gen/python`, never hand-written ones.

`.golangci.yml` (golangci-lint v2) applies to every Go module:
* **Linters**: the `standard` set plus `depguard`, `errorlint`, `misspell`, `nolintlint`, `unconvert`, `usestdlibvars`; generated code is excluded.
* **Formatters**: `gofumpt` and `goimports`, with `github.com/mavioai/mavio` imports in their own group.
* **depguard**: encodes the dependency direction from [Architecture §3.2](architecture.md#32-dependency-direction) as rules (`core` only on the standard library, pure libraries only on `core`, the plugin SDK only on `libs/proto`, no lib importing `apps/*` or `plugins/*`, …). To change the dependency direction, update the architecture document first, then the rules.

### 5.1 Cross-platform Paths

The server runs on Linux, macOS and Windows, and CI tests on all three (§6), so a path that only works with `/` as the separator fails only on Windows. The rules:
* **Recorded paths are slash-separated.** Library folders, the paths of items and media sources, `ExternalPath`, image paths and everything else the server records or compares holds a local path as `filepath.ToSlash(filepath.Clean(p))`, and a remote path (`core.RemoteScheme`) as it is. Handle them with `path`, never with `path/filepath`. Names within a storage (`core.Storage`, `fs.FS`) are slash-separated and relative, as `io/fs` requires.
* **Convert at the operating system's boundary only.** A path from the operating system (`t.TempDir`, `os.Executable`, `filepath.WalkDir`, a configuration file, a flag) goes through `filepath.ToSlash` before it is recorded or compared; a recorded path goes through `filepath.FromSlash` before an API that needs the native form, such as `os.OpenRoot` or a child process's arguments. `os` functions accept `/` on Windows as well.
* **Relate paths with the core helpers.** `core.StorageName` finds a file's name within a library folder, matching `/` with `\`, and `core.StoragePath` gives the recorded path back; test whether a path is absolute with `filepath.IsAbs` (or `core`'s Windows check), because `path.IsAbs("C:/x")` is false.
* **Never compare a recorded path with a `filepath.Join` result**: on Windows the two differ in separators. Compare recorded forms.
* **Tests record paths as the scanner does**: `root := filepath.ToSlash(t.TempDir())`, then `path.Join` below it. A test that stores `filepath.Join(t.TempDir(), …)` as an item's or a source's path passes on Linux and macOS but not on Windows.
* **Do not make folders read-only to make writes fail**: Windows ignores a folder's permission bits. A test that needs a write to fail puts a file where a folder must be made, which fails everywhere.

## 6. Continuous Integration

`.github/workflows/ci.yml` runs on pushes to `main` and on pull requests, and by hand from the Actions tab. Every job starts once **plan** has found what the change affects, and a job whose projects it does not affect is skipped; a change to `.github` or `mise.toml` affects every project, as does a run started by hand:
* **plan** (Linux): lists the affected Apple and Android projects, and whether the server or a library it is built from is affected.
* **check** (Linux): `nx affected -t buf-lint lint tidy-check typecheck build test`; regenerates code and fails on any diff; runs `buf breaking` against the base branch on pull requests.
* **test**: `nx run-many -t typecheck test build` on linux arm64, macOS and Windows; pull requests run `nx affected` instead.
* **apple** (macOS with Xcode 27, the runners' `xcode-27` image, as the `Package.resolved` files are made with Xcode 27), a job per platform, so that their builds do not share a runner's cores: **Apple (macOS)** for `libs/apple` and `apps/macos`, **Apple (iOS)** for `apps/ios`, **Apple (tvOS)** for `apps/tvos`, each when **plan** finds any of its projects affected. Each runs `nx run-many -t lint build test` over its affected projects, with the core built by the `dev` profile for its platform only, and fails when their generated Xcode projects differ from what `generate` writes.
* **android** (Linux), when **plan** finds Android projects affected: `nx run-many -t lint build test` over them, with the core built by the `dev` profile.
* **media** (Linux, macOS), when the server is affected: installs jellyfin-ffmpeg and rclone, generates the fixtures and runs the `media`, `streaming`, `rclone` and `server` tests without the Nx cache, so the ffmpeg and rclone integration and smoke tests run on the runners' hardware.
* **dist** (Linux), when the server is affected: `nx run server:dist`, so the server cross-compiles for every supported platform and is packaged with the pinned rclone; the platforms build in parallel, two at a time (`MAVIO_DIST_JOBS`), as more of them built afresh exhaust the runner's memory.
* **image** (Linux), when the server is affected: builds the container image for linux/amd64 and linux/arm64 without pushing it, then runs the amd64 image until its health check passes.

`.github/workflows/snapshots.yml` runs the snapshot tests of the clients ([Clients](clients.md) §6.8), started by hand from the Actions tab (`workflow_dispatch`) rather than on every push, as their references are recorded once the UI settles: **Web** (linux arm64, as the references are recorded on Apple silicon) runs `nx run web:snapshot`, then `design:gallery`, uploading the gallery and the results of the comparison; **iOS** (the `xcode-27` image, as the references are made with Xcode 27) runs `apple:snapshot` on the simulator, with the core built by the `dev` profile for the iOS simulator, uploading the snapshots that differ; **Android** (Linux) runs `android-lib:snapshot`, uploading the images of the snapshots that differ. Its jobs restore the caches of **ci.yml** and save none.

Toolchains in CI come from the same `mise.toml` (`jdx/mise-action`); jobs other than **media** leave jellyfin-ffmpeg and rclone out, and jobs other than **android** Java and Gradle (`MISE_DISABLE_TOOLS`). Rust comes from `rust-toolchain.toml` through the runners' rustup, and **check**, **test**, **apple** and **android** cache Cargo's builds (`Swatinem/rust-cache`), **apple** and **android** under a key of their core's profile, **apple** of its platform too. **apple** caches the clones of the Swift packages that SwiftPM and `xcodebuild` share (`~/Library/Caches/org.swift.swiftpm`), under a key of the `Package.resolved` files, and **android** Gradle's home, with its dependencies and build cache (`gradle/actions/setup-gradle`). **check**, **test**, **media** and **dist** cache Go's builds and modules, and **check** golangci-lint's results (`.github/actions/go-cache`): the caches are saved only on pushes to `main`, and pull requests restore the latest of them. **media** runs Go's tests with `-count=1`, so that their cached results do not replay. Caches are saved only on pushes to `main`; after the jobs of such a push, **caches** deletes the caches of `main` that newer ones replaced, those saved for earlier commits or toolchains, and `.github/workflows/pr-caches.yml` deletes a pull request's caches once it closes.

## 7. Releases and Versioning

`libs/proto` and `libs/plugin` are imported by third-party plugins and are published independently with path-prefixed tags (e.g. `libs/proto/v0.1.0`, `libs/plugin/v0.1.0`). Their `replace` directives have no effect on consumers, so:
1. Release `libs/proto` first.
2. Update the `require` of `libs/plugin` to that version, then release `libs/plugin`.

Other modules are used only inside the repository and promise no stable external API.

The server's release binaries are built with `VERSION=v0.1.0 pnpm nx run server:dist`, and its image with `docker buildx build -f apps/server/Dockerfile --build-arg VERSION=v0.1.0 --platform linux/amd64,linux/arm64 .` from the repository root. The Dockerfile pins the same jellyfin-ffmpeg version as `mise.toml`, with the SHA-256 digests of its two Linux portable builds; upgrading jellyfin-ffmpeg changes both files, and a test (`apps/server/internal/buildinfo`) fails when the two pins disagree. The image bundles the Linux builds of the mavioai/rclone release `mise.toml` pins in `/usr/local/bin/rclone`, checked against the same SHA-256 digests, which the same test compares. Releases of the fork are its tags `v<rclone version>-mavio` on its `mavio` branch, a single commit on top of the rclone release; pushing a tag runs the fork's `mavio release` workflow, which cross-compiles rclone without cgo for Linux, macOS and Windows on amd64 and arm64 and attaches the zips and `SHA256SUMS.txt` to the tag's release. Upgrading changes the version and the digests in both files. The image also builds the DLNA, indexers, download clients, subtitles and agent plugins and ships them in `/usr/lib/mavio/plugins`, the plugin seed folder; the agent plugin is compiled with the Bun version `mise.toml` pins, which the same test compares.

The clients' versions follow the server's: `MAVIO_VERSION`, `v0.1.0` or `0.1.0`, set for their builds makes it the release's, else a build is `0.0.0-` and the first 12 characters of the commit it is built at, else `dev`. The core's `build.rs` sets the core's (`mavio_core::VERSION`), which the apps show beside their own; the Android apps' builds set their `versionName` the same way, and their `versionCode` from a release's x.y.z as x×10000 + y×100 + z, else from the number of commits. The Apple apps and the Top Shelf extension do the same in the Version build phase of their Xcode projects (`libs/apple/scripts/version.sh`), which sets the built `Info.plist`'s `MavioVersion` to the version, `CFBundleVersion` to the same number, and `CFBundleShortVersionString` to a release's x.y.z, else 0.0.0, as the App Store requires. `MAVIO_VERSION` is an input of the Nx targets that build them, so that a release is never taken from the cache.

The first-party plugins are packaged by `tools/plugindist`, from their manifests: every plugin of `plugins/`, at the version in its manifest, as a catalog zip of its `manifest.json`, translations and executable, one per server platform for a process plugin — for a Python plugin, its whole folder with python-build-standalone's CPython and its dependencies, for the platforms they have wheels for, without pip, CPython's tests, headers and Tk, nor the packages the root `pyproject.toml` excludes (`exclude-dependencies`: resampy, numba and sympy, which Pipecat requires but the bundled services never import), and on Windows with `plugin.exe`, a Go launcher plugindist builds for each plugin that runs its console script on the folder's Python — and one for every platform for a WASM plugin, and a `catalog.json` listing them with their name, description and their translations, author, homepage, category and SHA-256 digests; a plugin without a category stops it. The first-party plugins are translated into the languages of the clients' strings: a test of `tools/plugindist` checks that every property of their configuration schemas has a title and that their `locales/zh-Hans.json` translates every string of their manifests. `pnpm nx run plugindist:dist` builds them all into `tools/plugindist/dist/`, with URLs relative to the catalog, as a release publishes them; `-platforms` limits the platforms.

The official catalog is the `catalog.json` of the latest release of the mavioai/plugins repository, which the server's `plugin-catalog` setting defaults to; its releases hold the packages `plugindist:dist` builds from the source of a Mavio release. For a development server, `pnpm nx run plugindist:catalog` builds the plugins for this platform into each plugin's `dist/` and writes `plugins/catalog.json` (ignored by Git), whose packages are file URLs; the server started with `--plugin-catalog ../../plugins/catalog.json` installs from it.

While a plugin is developed, `pnpm nx run <plugin>:dev` builds it for this platform into its `dist/dev`, and again whenever its sources or those of the in-repo modules it depends on change; a server started with `--plugin-dev <absolute path of plugins/<name>>` (several separated as `PATH` is) runs it from there in place of an installed one and restarts it once the folder changes, and its screen in the web UI has a Restart button and its logs ([Plugins §13](plugins.md#13-developing-plugins)).

Release builds of `scraper-tmdb` set `MAVIO_TMDB_KEY` to Mavio's own TMDB API key, which `pnpm nx run scraper-tmdb:build` builds into the plugin as the key used once TMDB rejects Radarr's token ([Architecture §13.2](architecture.md#132-data-sources-and-numbering)); the key is never committed.

## 8. Commits and Documentation

* Use Conventional Commits with the Nx project name as scope: `feat(naming): parse absolute episode numbers`, `build(nx): …`, `docs: …`. Keep each commit to a single purpose, and make sure `pnpm nx affected -t build test lint tidy-check` passes before committing.
* Every document exists in English (`<name>.md`) and Simplified Chinese (`<name>.zh-CN.md`) with section-by-section correspondence; the two link to each other at the top, and both are updated in the same commit.
