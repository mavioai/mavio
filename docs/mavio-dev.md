# mavio.dev

> English | [简体中文](mavio-dev.zh-CN.md)

> Related: [Accounts](accounts.md) · [Architecture](architecture.md) · [Roadmap](roadmap.md) · [AGENTS.md](../AGENTS.md)

> The central service of servers in mavio.dev mode: what it runs, how it reaches servers, how servers get names and certificates, the relay, and where each part is deployed. What it holds and the account model it serves are described in [Accounts](accounts.md). It is built in phase P28 of the [Roadmap](roadmap.md).

---

## 1. Overview

mavio.dev is the OpenID Connect issuer of servers in mavio.dev mode ([Accounts §3.2](accounts.md#32-servers-and-claiming)): it keeps their access records and pushes changes and revocations to them, signs in televisions with codes, and runs the relay, certificates and discovery for those servers. It is made of three applications:

| Application | What it is |
| :--- | :--- |
| `apps/website` | The website and its API: accounts, servers, access records, friends, Homes, Mavio Pass, the push to servers and ACME challenges (§2, §3) |
| `apps/dns` | The name servers of `mavio.site` (§4) |
| `apps/relay` | The relay for servers that cannot be reached directly (§5) |

## 2. Website and API (`apps/website`)
* A TanStack Start application on Cloudflare Workers, deployed with Cloudflare's `cf` command line. The pages use TanStack Query; the data is in PostgreSQL, reached through Hyperdrive with Drizzle over `pg`, with one database client per request. The schema is in `src/server/db`: better-auth's tables, generated by its `auth` command line (`pnpm --filter @mavio/website generate-auth-schema`), and Mavio's own; drizzle-kit writes their migrations into `drizzle/` (`generate-migration`). The API is served under `/api`: better-auth at `/api/auth`, the OAuth endpoints of devices' sessions at `/api/oauth/token`, `/api/oauth/device` and `/api/oauth/revoke` ([Accounts §6](accounts.md#6-signing-in)), the site's configuration at `/api/config`, and the Connect services at `/api/mavio.cloud.v1.*`, whose requests are checked with protovalidate. The OAuth endpoints, `/api/config`, `AccountService`, `FriendService` and `HomeService` answer requests from any origin, since app.mavio.dev and servers' web UIs call them.
* Accounts are built on better-auth: an e-mail address or user name with a password, passkeys, TOTP as the second factor, bearer sessions, and its JWT plugin, whose key set servers fetch to check sign-in assertions.
* **Devices' sessions** ([Accounts §6](accounts.md#6-signing-in)) are Mavio's own: a row per session with its account, client ID and device key. An access token is `mds1.<claims>.<signature>`, the claims naming the session, the account and an expiry ten minutes on, signed with HMAC-SHA256 under better-auth's secret; every request checks that its session still exists, so that ending one takes effect at once. The Connect services take these tokens as well as better-auth's sessions.
  * `/api/oauth/token` starts a session for an authorization code, whose `client_id` is a server's ID, refused once the account no longer administers the server, or `app`; for an approved link code, with the grant `urn:ietf:params:oauth:grant-type:device_code` and RFC 8628's answers while it waits; and renews one with the grant `urn:mavio:params:oauth:grant-type:device-signature`, given the session ID, a time in milliseconds later than its last renewal and within two minutes of mavio.dev's, and the device key's Ed25519 signature of `mavio-dev-renew-v1`, a zero byte, the session ID, a zero byte and the time. It answers with the access token, its lifetime, the session ID and the account.
  * `/api/oauth/device` gives a link code to a device key of Mavio's own clients (`app`, `dev.mavio.*`) or of a server's web UI (its ID): a user code `XXXX-XXXX` to enter at `/link` and a device code to poll with, valid for ten minutes and polled at most every five seconds. A server's link code is approved only by its administrator.
  * `/api/oauth/revoke` ends the session of an access token, expired or not.
* Passwords are hashed through better-auth's `password.hash` and `password.verify` with scrypt from `node:crypto` (N = 16384, r = 16, p = 1, a 64-byte key), stored in PHC format, and hashed again at sign-in when the parameters change.
* A managed account is a better-auth user that `HomeService` inserts with the kind `managed`, its restriction profile and the e-mail value `managed:<id>`, which no sign-in accepts, since only the public routes require a valid e-mail address; it has no credential, and a hook of Mavio's better-auth plugin refuses it the endpoints that change names, e-mail addresses, passwords, passkeys and TOTP or delete the account. Converting it into a full account sets a real e-mail address and a password, and sends the change to its servers.
* The pages call `mavio.cloud.v1.FriendService` and `mavio.cloud.v1.HomeService` too. Friends are requested by user name or e-mail address and accepted by either adding the other back or accepting; granting access to an account that is not a friend requests it. A Home holds at most 15 accounts, its administrator included, and pending invitations count towards them. An invitation needs the administrator's Mavio Pass and offers access records on the administrator's servers, which take effect when it is accepted; joining another Home leaves the current one, and a Home's administrator must dissolve it first. A full member who leaves or is removed becomes the administrator's friend; a managed account removed, or in a dissolved Home, is deleted with an `AccountRevoked` of reason deleted to its servers, and an account administering a Home cannot be deleted. The administrator's grants to a managed account of the Home take effect at once, on its own servers only.
* Switching is `POST /api/auth/home/switch` of Mavio's better-auth plugin, with the target's account ID and its PIN or, after too many wrong PINs, its password: it creates a session for the target, sets its cookie (and its bearer token for native clients) and deletes the device's previous session. PINs are hashed as passwords are; from the third wrong PIN, switching to the account waits 30 seconds, doubling to at most 15 minutes, and after five wrong PINs switching to a full account needs its password. Mavio Pass is a table of expiry times per account, which `GetAccount` reports with whether the account's Pass is effective; a Home is frozen while its administrator has none.
* Mavio's own parts: claiming and `private_key_jwt`, sign-in assertions, library access records and invitations, friends, Homes, switching with PINs, Mavio Pass, the push to servers, the ACME challenges of §4.2 and relay tickets (§5).
* Servers call the Connect service `mavio.cloud.v1.ServerService` (`libs/proto`) under the API's base URL, `https://mavio.dev/api` unless a server's `mavio-dev-url` names another: `CreateClaimRequest` records a claim request for the web UI that started it, with its redirect URI, PKCE challenge, device key and state, and returns its page, `/claim?request=…`; `ClaimServer` returns the outcome of a claim request once its account confirmed it, or registers a server's identity public key under the account of a claim code, and returns that account with the server's current cursor; `ListChanges` gives a claimed server's changes after a cursor, and `PublishLibraries` replaces the IDs, names and kinds of the server's libraries that mavio.dev keeps, and `PublishConnections` the URLs clients reach the server at, which `ListServers` gives its accounts. A change is an access record granted, with the account and the record; access revoked; an account's name changed; or an account suspended, deleted or reported compromised. Every request carries a JWT the server signs with its identity key (`private_key_jwt`) as a bearer token: EdDSA, with the server's ID ([Accounts §5.1](accounts.md#51-server-identity)) as its `kid`, `iss` and `sub`, the base URL as its `aud`, a random `jti` and an expiry a minute after it was issued.
* Sign-in assertions ([Accounts §5.5](accounts.md#55-sign-in-assertions)) are EdDSA JWTs signed with the keys of better-auth's JWT plugin, published at `/auth/jwks` under the API's base URL: `iss` is the base URL, `aud` the server's ID, `sub` the account's ID, `iat` and `exp` at most two minutes apart, `device_key` the device's public key in unpadded base64url and `nonce` a random value. The device signs `mavio-sign-in-assertion-v1`, a zero byte and the assertion. Servers cache the key set for its `Cache-Control` max-age, an hour without one, and fetch it again, at most once a minute, for an unknown `kid`.
* The website's pages call the Connect service `mavio.cloud.v1.AccountService` with the account's session: `GetClaimRequest` and `AnswerClaimRequest` show a claim request at `/claim` and confirm or cancel it, a full account's confirmation registering the server and sending the browser back with an authorization code; `CreateClaimCode` gives a claim code for a server without a browser, eight characters `XXXX-XXXX` without look-alike characters, valid for ten minutes and stored as a hash; `GetLinkCode` and `AnswerLinkCode` show a link code at `/link` and approve or deny it; `ListServers` and `RemoveServer` list the servers the account administers or reaches and remove one; `CreateAssertion` signs a sign-in assertion for a server the account has access to and a device key; `CreateAuthorizationCode`, called by `/authorize`, gives a code valid for a minute, stored as a hash with the redirect URI, the PKCE challenge and the device key, which `/api/oauth/token` exchanges once for a session: to a server's web UI only when the account administers the server, after the account approves, and to app.mavio.dev at once when the redirect URI is at its address; `ListAccess`, `GrantAccess` and `RevokeAccess` manage a server's access records for its administrator; `ListInvitations`, `AcceptInvitation`, `DeclineInvitation` and `LeaveServer` serve the account they are for; `ReportCompromised` ends the account's sessions, devices' sessions included.
* Granting access to an account creates an invitation; the access record takes effect, and its server receives the change, once the account accepts it. Changing an accepted record sends it again, and revoking or leaving it sends its revocation. A server claimed by another account sends the revocation of its former administrator's access. Changing an account's name sends the change to the servers it reaches; deleting an account sends its revocation, and is refused while it administers servers; reporting it compromised sends a revocation of its own kind.

## 3. Push to Servers
* Each server in mavio.dev mode has a Durable Object holding the server's WebSocket connection. The connection hibernates between messages and is kept alive with protocol pings, which do not wake the object.
* Every change for a server ([access records](accounts.md#33-library-access), revocations, Home and account deletions) is stored with an increasing cursor. The Durable Object only notifies the server that its changes reached cursor N; the server then fetches the changes after its own cursor over HTTPS, with a request signed by its identity key.
* The server opens the WebSocket at `/servers/notices` under the API's base URL with the same JWT as its requests; each notice is a binary frame holding a `mavio.cloud.v1.Notice`. The server pings every 30 seconds, and a failed ping ends the connection.
* The server also fetches its changes whenever it reconnects, with exponential backoff and jitter, and every six hours, so that a lost notice delays a change but never loses it.
* The Durable Object is the class `NoticeHub`, exported by the Worker's entry `src/server.ts` beside TanStack Start's handler and named after the server's ID. The Worker checks the server's JWT before it hands the WebSocket to the object, which replaces an older connection of the same server. Every change a request records is noted, and once the request is done the Worker tells each server's object its latest cursor (`waitUntil`), so that a notice never runs ahead of the transaction that recorded the change.

## 4. Certificates and Subdomains

### 4.1 Names
* Servers' names are under `mavio.site`, which is on the Public Suffix List, so that browsers keep the cookies and storage of different servers apart.
* A server in mavio.dev mode has the names `<address>.<ID>.mavio.site`, one for each of its addresses: IPv4 addresses are written with dashes (`192-168-1-10`), IPv6 addresses with dashes for colons (`2001-db8--1`).
* `apps/dns` is a stateless Go service built on `miekg/dns` that serves `mavio.site` from two VMs, its name servers. It computes A and AAAA answers from the name, answers relay names with their region's relay addresses (§5), and serves a static SOA and NS, the `_psl` TXT record and CAA records allowing Let's Encrypt and Google Trust Services. It answers `_acme-challenge.<ID>.mavio.site` with a CNAME to `<ID>.acme.mavio.dev`.
* An ID is a label of 32 lowercase base32 characters; under it, an address label that is not an IPv4 address with dashes or an IPv6 address with dashes for colons, a relay name of an unknown region, and every other name are answered as not existing, with the SOA. The service listens over UDP and TCP (`--addr`, `:53` by default) and reads its configuration from a JSON file (`--config`): the zone, its name servers with their addresses, the SOA's mailbox and serial, the ACME domain, the `_psl` value, the CAs of the CAA records, the relays' addresses by region and the TTLs, an hour for computed and static records and five minutes for relay names.

### 4.2 Certificates
* Each server has one wildcard certificate, `*.<ID>.mavio.site`, from Let's Encrypt through ACME's DNS-01 challenge, which the server runs itself with `golang.org/x/crypto/acme`. The certificate's key is generated on the server and never leaves it.
* The server sends the challenge's TXT value to mavio.dev in a request signed with its identity key (`ServerService.SetAcmeChallenge`); mavio.dev accepts it for that server's own ID only, writes the TXT record `<ID>.acme.mavio.dev` in its Cloudflare zone through the Cloudflare API, and deletes it once the challenge is done (`ClearAcmeChallenge`). The server waits ten seconds after publishing the value before it asks the CA to check it.
* The server renews the certificate at two thirds of its lifetime, or earlier at a random time in the window that ACME Renewal Information suggests, and turns to Google Trust Services when Let's Encrypt fails. Google Trust Services requires an external account binding to register the server's ACME account, which mavio.dev mints through Google's Public CA API as a service account of its Google Cloud project (`ServerService.CreateAcmeBinding`). A failed attempt is retried after ten minutes, doubling to six hours.
* A claimed server keeps the certificate, its key and one ACME account key per CA in `certificate-dir` (`certificates/` in its home), tries the CAs of `acme-directories` in order, and serves HTTPS on the HTTPS port of its network settings, 8920 by default, with the certificate whenever the settings name no certificate files of their own. It serves the certificate through `tls.Config.GetCertificate`, so a renewal takes effect without a restart.

### 4.3 Connecting
Browsers reach a server by its names through DNS. Native clients connect to an address directly, with the address's name as the TLS server name, so that they also work where DNS answers with private addresses are filtered, and they check the server's identity key as well ([Accounts §5.1](accounts.md#51-server-identity)).

## 5. Relay (`apps/relay`)
* A Go service on VMs in Europe, the United States and Singapore, for servers that cannot be reached directly. A server whose relay use is allowed keeps a connection to the relay of its region.
* A client reaches the server through the relay at `relay-<region>-<ticket>.<ID>.mavio.site`. The ticket is issued by mavio.dev, valid for a few minutes, and only when the viewer or the server's administrator has an effective Mavio Pass ([Accounts §3.7](accounts.md#37-mavio-pass)).
* The relay reads the name from the TLS ClientHello, checks the ticket and splices the client's connection to the server's without terminating TLS, so encryption stays end to end and the relay sees only encrypted bytes.

### 5.1 Tickets
* A client asks for a ticket with `AccountService.CreateRelayTicket`, which answers with the host name to connect to and its expiry. mavio.dev gives one when the account administers the server or holds an accepted access record, the server has recorded a relay region, and the viewer or the administrator has an effective Mavio Pass.
* A ticket is the expiry, five minutes ahead, in Unix seconds as four big-endian bytes, followed by the first 16 bytes of an HMAC-SHA256 of `mavio relay ticket`, the server's ID, the region and those four bytes, separated by zero bytes, under a secret mavio.dev shares with the relays; it is written in lowercase base32 without padding, 32 characters. The relay checks it against the name's ID and its own region, so a ticket admits connections to one server through one relay; connections opened before the expiry stay open.

### 5.2 Servers' connections
* A server keeps a connection to a relay while it is claimed, has its certificate, and its network settings allow the relay (on by default). It lists the relays with `ServerService.ListRelays`, picks the one that accepts a TCP connection soonest, and records its region with `ServerService.SetRelayRegion`, which it clears when it stops; mavio.dev gives tickets only for a recorded region.
* The relay serves clients on one port (443) and servers on another, over HTTPS. A server opens its control connection with `GET /servers/connect`, upgraded to the `mavio-relay` protocol, carrying its public identity key in `Mavio-Identity-Key` and a JWT it signs for the relay's URL as for mavio.dev (§2); the relay checks that the key hashes to the ID and verifies the JWT, so it needs no database. A newer control connection of a server replaces the older one.
* On the control connection the relay writes 16-byte frames: a connection's random ID for each client, or zeros every 30 seconds as a heartbeat; a server that hears nothing for 90 seconds reconnects. For each ID the server opens `GET /servers/accept` with the ID in `Mavio-Relay-Connection`, which only the server announced to may take; the relay sends it the client's ClientHello and copies bytes both ways, and the server serves TLS with its certificate and its HTTP handler on the connection.
* The relay is a stateless Go program (`--region`, `--url`, the base URL the servers' JWTs name, `--ticket-secret-file`, `--addr` for clients, `--server-addr` with `--cert` and `--key` for servers, `--zone`). A failed connection is retried after five seconds, doubling to ten minutes.

## 6. Deployment

| Where | What |
| :--- | :--- |
| Cloudflare | `apps/website` on Workers; the Durable Objects of §3; the `mavio.dev` DNS zone; R2 for downloads of Mavio releases; reachability checks of servers' published addresses with Workers' outbound TCP connections; e-mail through Cloudflare Email Service |
| VMs | PostgreSQL, with a streaming replica and its WAL archived to R2; `apps/relay`; `apps/dns` |

The Worker is built, run in development and deployed with Cloudflare's `cf` command line, a development dependency of `apps/website`, and its configuration is `apps/website/cloudflare.config.ts`: the `BASE_URL` variable, the `APP_URL` variable, app.mavio.dev's address (`https://app.mavio.dev` unless set), the Hyperdrive binding, whose ID is the configuration created for the database, the `NOTICES` binding of the `NoticeHub` Durable Object, exported with SQLite storage, the `ACME_DOMAIN` variable (`acme.mavio.dev`), and the secrets `BETTER_AUTH_SECRET`, `CLOUDFLARE_ZONE_ID` and `CLOUDFLARE_API_TOKEN`, a token allowed to edit the zone's DNS records, `GOOGLE_CA_PROJECT` and `GOOGLE_CA_CREDENTIALS`, the key file of a service account allowed to create external account keys, and `RELAY_TICKET_SECRET`, the relays' ticket secret, each set with `cf workers secrets update`; without the Cloudflare secrets the ACME methods are unimplemented. The `RELAYS` binding, a JSON binding listed in the configuration once relays run, holds the relays' base URLs by region, each the `--url` of its relay; without it or the ticket secret there are no relays and tickets are unimplemented. Its entry is `src/server.ts`. The types of the Worker's bindings and of the Workers runtime are generated from the configuration into `.cloudflare/types` by `cf workers types`, which `typecheck` runs, and by the build. `pnpm --filter @mavio/website build` (`cf build`) writes the Worker to `.cloudflare/output`, and `deploy` (`cf deploy`) builds and deploys it. In development, `pnpm --filter @mavio/website dev` (`cf dev`) runs the Worker in workerd through Vite against the PostgreSQL of the binding's development connection string, such as a container of `postgres:17-alpine` with user, password and database `mavio` on port 5432, migrated with `DATABASE_URL=postgres://mavio:mavio@localhost:5432/mavio drizzle-kit migrate`, with `BASE_URL` set to `http://localhost:5173` in the development mode and the secret in `apps/website/.env.local`, which is not committed; a server reaches it with `--mavio-dev-url http://localhost:5173/api`.

## 7. Security Notes

* **mavio.dev controls `mavio.site`** and could have certificates issued for a server's names; native clients also check the server's identity key, which mavio.dev does not hold the private half of.
* **The relay** sees which server a client reaches and how much it transfers, never the content.
* What a compromised mavio.dev could do to servers is described in [Accounts §10](accounts.md#10-security-notes).
